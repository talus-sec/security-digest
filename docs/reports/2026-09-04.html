Scoped Vulnerability Tracking

Database

The single most urgent item in today's database digest is CVE-2026-9586 under the PostgreSQL bucket — it's the only CISA KEV-confirmed actively exploited entry, a SQL injection in Sangoma Switchvox that lets an unauthenticated remote attacker run arbitrary SQL against the backend PostgreSQL database (with a CISA due date of 2026-09-05). Beyond that, PostgreSQL carries the bulk of the high-severity formal CVEs this cycle, including a critical 10.0 (Versa Director), a 9.8 (R2R), and several other SQL injection issues in third-party products. MySQL's Connector/Net and Connector/J also surface multiple high-severity Oracle CPU entries, and a shared Grafana CVE (CVE-2026-19475) impacts PostgreSQL, MySQL, and SQL Server data sources.

Formal Vulnerabilities

PostgreSQL — CVE-2026-9586 (CVSS UNSCORED — CISA-confirmed active exploitation) 🔴 ACTIVELY EXPLOITED (CISA KEV)

Summary: An unauthenticated remote attacker can send a single crafted request to Sangoma Switchvox and execute arbitrary SQL statements against the backend PostgreSQL database, with potential escalation to remote code execution. CISA added this to KEV on 2026-09-02 with a remediation due date of 2026-09-05 and requires mitigation per BOD 26-04 or discontinuing use of the product.

Affected Features / Interoperability: Switchvox's PostgreSQL backend is fully exposed to the SQLi; downstream PBX call data, configurations, and credentials stored in Postgres are reachable. The raw data does not specify which Switchvox versions or modules are affected beyond the vendor product as a whole.

Source: https://nvd.nist.gov/vuln/detail/CVE-2026-9586

Actions:

  • Fix: No patched version supplied in the data — follow Sangoma's vendor instructions as referenced in CISA KEV.
  • Workaround: Discontinue use of the product if mitigations are unavailable; otherwise, isolate Switchvox from any network reachable by untrusted actors, monitor Postgres logs for anomalous statements, and ensure Postgres is not directly reachable from outside the Switchvox host.
  • Tradeoff: Discontinuing use of Switchvox disrupts telephony; network isolation may break legitimate admin workflows. Both are preferable to confirmed unauthenticated RCE-to-SQL exposure.
PostgreSQLCVE-2024-42450CVSS 10.0 · CRITICAL

Summary: Versa Director ships with a default shared Postgres password and, by default, listens on all network interfaces. An unauthenticated attacker can connect and administer the Postgres database or read local filesystem contents for privilege escalation. Exploitation status is "proof of concept in lab" per Versa, but the impact ceiling (full DB admin + privesc) earns the 10.0.

Affected Features / Interoperability: Versa Director's Postgres holds operational/configuration data and is required for High Availability; compromise of the database breaks HA functionality and exposes all SD-WAN operational state.

Source: https://security-portal.versa-networks.com/emailbulletins/6735a300415abb89e9a8a9d3

Actions:

  • Fix: Upgrade to Versa Director 22.1.4 or later (auto-restricts Postgres/HA ports to peer directors).
  • Workaround: For older releases, perform manual HA-port hardening per https://docs.versa-networks.com/Solutions/System_Hardening/Perform_Manual_Hardening_for_Versa_Director#Secure_HA_Ports, change the default Postgres password, and bind Postgres to localhost/internal interfaces only. Follow Versa's published Firewall guidelines.
  • Tradeoff: Manual hardening increases operational complexity and HA port restriction may break HA peering if not applied symmetrically across the director cluster.
PostgreSQLCVE-2026-82526CVSS 9.8 · CRITICAL

Summary: R2R (through 3.6.6) has a stacked SQL injection in its vector index creation endpoint. The `index name` parameter is string-formatted directly into a `CREATE INDEX` statement without quoting or an allowlist, letting an unauthenticated attacker execute arbitrary DDL/DML — including semicolon-separated statements — under the PostgreSQL superuser.

Affected Features / Interoperability: Vector index creation endpoint; downstream Postgres superuser means full read/write across all databases R2R manages, including any embedded credential stores or application data.

Source: https://github.com/SciPhi-AI/R2R/issues/2309, https://www.vulncheck.com/advisories/r2r-sql-injection-via-vector-index-creation-endpoint

Actions:

  • Fix: Upgrade R2R beyond 3.6.6 (the data doesn't list a specific fixed version; check the project's GitHub).
  • Workaround: Restrict network access to the vector index creation endpoint, front it with authentication, and run the R2R Postgres role with least privilege rather than superuser.
  • Tradeoff: Reducing the Postgres role from superuser may break R2R features that legitimately require DDL-level permissions.
PostgreSQLCVE-2026-72775CVSS 8.8 · HIGH

Summary: n8n before 1.123.67 / 2.31.5 / 2.32.1 has a SQL injection in the PostgresTrigger node. User-supplied channel, function, and trigger names are interpolated into SQL statements without escaping, letting an authenticated n8n user run arbitrary SQL against the connected Postgres database with the configured credential's privileges.

Affected Features / Interoperability: PostgresTrigger node specifically; downstream Postgres databases used by n8n workflows are exposed, including any data the workflow credential can reach.

Source: https://github.com/n8n-io/n8n/security/advisories/GHSA-jqwr-vx3p-r266, https://www.vulncheck.com/advisories/n8n-before-sql-injection-via-postgrestrigger-node

Actions:

  • Fix: Upgrade n8n to 1.123.67, 2.31.5, or 2.32.1 or later.
  • Workaround: Restrict who can author PostgresTrigger nodes (RBAC), and use a dedicated least-privileged Postgres role for n8n's connection.
  • Tradeoff: A least-privileged role will lose access to schemas/triggers outside its grant, which may break existing workflows.
PostgreSQLCVE-2026-85388CVSS 8.1 · HIGH

Summary: Worklenz (through 3.0.0) fails to validate the `sort-field` query parameter in pagination helpers, allowing authenticated users to inject arbitrary Postgres expressions into `ORDER BY` clauses. Time- and blind-based extraction can leak data — including password hashes from other tenants — across tenant boundaries. Described as an incomplete fix for CVE-2026-25947.

Affected Features / Interoperability: Pagination/sorting helpers across Worklenz controllers; multi-tenant data isolation is broken at the database layer, including cross-tenant credential exposure.

Source: https://github.com/Worklenz/worklenz/security/advisories/GHSA-f2f8-2ppj-85pf, https://github.com/Worklenz/worklenz/blob/v3.0.0/worklenz-backend/src/controllers/job-titles-controller.ts

Actions:

  • Fix: Upgrade Worklenz beyond 3.0.0 (the data doesn't list a specific fixed release; track the GHSA).
  • Workaround: Restrict Worklenz to trusted authenticated users only and add a WAF/reverse-proxy rule to strip non-alphanumeric characters from `sort-field` parameters.
  • Tradeoff: Strict input filtering on `sort-field` may break legitimate UI sorting on custom columns.
PostgreSQLCVE-2026-19475CVSS 6.5 · MEDIUM

Summary: An authenticated Grafana user who can query a SQL data source can bypass the fix for CVE-2026-33375 by injecting the `timeGroup` macro via a WHERE clause; evaluating it causes uncontrolled memory consumption that terminates the Grafana server (DoS). Microsoft SQL Server, PostgreSQL, and MySQL data sources are all affected.

Affected Features / Interoperability: Grafana SQL data-source macro expansion; the crash takes down the Grafana server process, breaking all dashboards relying on that instance.

Source: https://grafana.com/security/security-advisories/cve-2026-19475

Actions:

  • Fix: Apply the Grafana patch referenced in the security advisory (specific version not given in the data).
  • Workaround: Restrict who can author or edit SQL data-source queries in Grafana; consider read-only roles for dashboards.
  • Tradeoff: No significant tradeoff beyond limiting data-source edit privileges.
PostgreSQLCVE-2026-85689CVSS 6.5 · MEDIUM

Summary: llmware 0.4.6 string-interpolates filter/lookup values into SQL WHERE clauses without parameterization in both SQLite and PostgreSQL backends. The validator only allow-lists keys, never sanitizes values. On Postgres this enables boolean- and UNION-based SQLi; on SQLite it enables cross-collection/cross-document disclosure.

Affected Features / Interoperability: llmware `Library.block_lookup`, `Query.text_query_with_custom_filter`, and `Query.text_query_by_author_or_speaker`; any Postgres database backing llmware is exposed.

Source: https://github.com/llmware-ai/llmware/issues/1304, https://www.vulncheck.com/advisories/llmware-0.4.6-sql-injection-via-unescaped-filter-values

Actions:

  • Fix: Upgrade llmware beyond 0.4.6 (specific version not in the advisory).
  • Workaround: Run llmware against a dedicated least-privileged Postgres role and isolate the public API from untrusted callers.
  • Tradeoff: A restricted Postgres role may reject some legitimate collection operations that require broader DML.
