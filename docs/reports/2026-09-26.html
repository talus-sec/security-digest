Scoped Vulnerability Tracking

Database

The most urgent item is CVE-2026-85878 in Azure Database for PostgreSQL (CVSS 9.9 CRITICAL), an improper authorization flaw allowing an authenticated attacker to elevate privileges over the network. No CISA KEV-confirmed exploits appear in today's feed; the next-highest severities are MySQL CVE-2025-67510 (9.4) and two Microsoft SQL Server issues (8.4/8.3) tied to insecure defaults in NMIS/BioDose medical deployments.

Formal Vulnerabilities

MySQLCVE-2025-67510CVSS 9.4 · CRITICAL

Summary: The Neuron PHP framework's `MySQLWriteTool` (versions ≤2.8.11) executes arbitrary SQL supplied by an LLM/agent caller via `PDO::prepare()` without semantic restrictions. Prompt injection or indirect prompt manipulation can trigger destructive queries (DROP, TRUNCATE, DELETE, ALTER, privilege statements) subject to the DB user's permissions. Deployments exposing an agent with this tool to untrusted input and/or using a highly privileged DB account are impacted.

Affected Features / Interoperability: Neuron AI framework's `MySQLWriteTool` component; any LLM agent workflow that accepts untrusted prompts and connects to MySQL/MariaDB. Downstream impact includes potential data destruction, schema alteration, and privilege escalation within the database.

Source: https://github.com/neuron-core/neuron-ai/commit/44bab85d92bf162898ee48d0bcef6ba0d29b59c9, https://github.com/neuron-core/neuron-ai/releases/tag/2.8.12, https://github.com/neuron-core/neuron-ai/security/advisories/GHSA-898v-775g-777c

Actions:

  • Fix: Upgrade Neuron to version 2.8.12.
  • Workaround: Restrict the DB account used by the tool to least-privilege (read-only or specific DML only); disable `MySQLWriteTool` if not required.
  • Tradeoff: Least-privilege DB accounts may break legitimate agent write operations; disabling the tool removes write capability entirely.
MySQLCVE-2025-67509CVSS 8.2 · HIGH

Summary: Neuron's `MySQLSelectTool` (≤2.8.11) validates only the first keyword (e.g., SELECT) and a forbidden-keyword blocklist, which fails to block `INTO OUTFILE` / `INTO DUMPFILE` constructs. An attacker influencing tool input (e.g., via prompt injection) can write arbitrary files to the DB server if the MySQL/MariaDB account holds the `FILE` privilege and server configuration permits writes to accessible locations (e.g., web root).

Affected Features / Interoperability: Neuron AI framework's `MySQLSelectTool`; MySQL/MariaDB `FILE` privilege and `secure_file_priv` configuration. Downstream impact: arbitrary file write on the database host, potential web-shell deployment.

Source: https://github.com/neuron-core/neuron-ai/commit/72735d0ea133266cf2f5d5d195d41e9dd865289a, https://github.com/neuron-core/neuron-ai/releases/tag/2.8.12, https://github.com/neuron-core/neuron-ai/security/advisories/GHSA-j8g6-5gqc-mq36

Actions:

  • Fix: Upgrade Neuron to version 2.8.12.
  • Workaround: Revoke `FILE` privilege from the DB account; set `secure_file_priv` to a non-web-accessible directory or NULL.
  • Tradeoff: Revoking `FILE` may break legitimate `SELECT ... INTO OUTFILE` workflows; `secure_file_priv` changes require server restart and may affect other applications.
MySQLCVE-2026-100683CVSS 8.0 · HIGH

Summary: Budibase (<3.45.0) builds MySQL/MSSQL column-rename DDL by interpolating identifiers directly into raw query strings without using the project's quoting helpers. An attacker with DDL rights on a connected datasource can create a column name containing a backtick (MySQL) or single quote (MSSQL) plus injected SQL; when a builder later renames that column via the UI, the embedded quote terminates the identifier and the injected SQL executes. MySQL connections use `multipleStatements: true`, enabling stacked statements as the datasource user.

Affected Features / Interoperability: Budibase backend-core SQL table rename logic (`sqlTable.ts`); MySQL and MSSQL datasources. Downstream impact: arbitrary read/write/destructive operations on the connected database outside Budibase's permission model.

Source: https://github.com/Budibase/budibase/security/advisories/GHSA-ppj8-hmx2-m546, https://www.vulncheck.com/advisories/budibase-before-3.45.0-sql-injection-via-column-rename-ddl

Actions:

  • Fix: Upgrade Budibase to 3.45.0.
  • Workaround: Restrict DDL privileges for Budibase datasource users; avoid allowing untrusted users to create/rename columns.
  • Tradeoff: Restricting DDL may break legitimate schema migration workflows managed through Budibase.
MySQLCVE-2026-100698CVSS 5.8 · MEDIUM

Summary: Adminer 5.5.1–6.0.1 improperly parses the login `server` string in `host_port()`. The port regex requires pure digits at string end; a non-digit tail causes fallback to the whole string as host with empty port. The privileged-port check inspects only the parsed port, so it is bypassed. The MySQL client then re-parses `host:port` from the host string, allowing a remote unauthenticated attacker to submit values like `127.0.0.1:80/x` and make the server initiate TCP connections to arbitrary internal hosts/ports before authentication — enabling SSRF and blind internal port scanning.

Affected Features / Interoperability: Adminer login page `server` field parsing; MySQL/mysqli client connection logic. Downstream impact: internal network reconnaissance, access to privileged ports, potential pivot to internal services.

Source: https://github.com/vrana/adminer/security/advisories/GHSA-rwxg-xph9-82cj, https://www.vulncheck.com/advisories/adminer-before-6.0.2-privileged-port-ssrf-via-host-port-regex

Actions:

  • Fix: Upgrade Adminer to 6.0.2.
  • Workaround: Restrict Adminer access to trusted networks only; deploy behind VPN/zero-trust proxy; block outbound connections from the Adminer host to internal ranges.
  • Tradeoff: Network restrictions may limit legitimate remote administration; outbound blocking may break legitimate cross-service connectivity.
MySQLCVE-2026-76803CVSS 5.3 · MEDIUM

Summary: Nuclei vulnerability scanner (3.0.0–3.10.0) does not enforce the local-file sandbox when a JavaScript template supplies the `allowAllFiles` MySQL DSN option. An untrusted JavaScript template scanning an attacker-controlled MySQL-compatible endpoint can cause the server to issue `LOAD DATA LOCAL INFILE` requests for arbitrary paths; the scanner's client reads the files and returns contents even with `-allow-local-file-access` disabled. JavaScript templates can run unsigned without `-code` flag on affected versions.

Affected Features / Interoperability: Nuclei `nuclei/mysql` JavaScript library; CLI and SDK deployments accepting untrusted templates. Downstream impact: arbitrary file read from the scanner host filesystem.

Source: https://github.com/projectdiscovery/nuclei/commit/9611926a9a1ca99e8ed554d1b26fbeff60e06368, https://github.com/projectdiscovery/nuclei/pull/7473, https://github.com/projectdiscovery/nuclei/releases/tag/v3.10.0, https://github.com/projectdiscovery/nuclei/security/advisories/GHSA-xhmx-w2j4-rw3q

Actions:

  • Fix: Upgrade Nuclei to 3.10.0.
  • Workaround: Disable JavaScript template execution (`-code` flag only); do not run untrusted templates; restrict scanner network egress.
  • Tradeoff: Disabling JS templates reduces scanning flexibility; network egress restrictions may break legitimate scanning targets.

Summary: The `mysqlnd` wire protocol parser reads fields from server packets before verifying the packet contains enough bytes. A malicious or compromised MySQL server can send a truncated packet, causing the client to read past the buffer end — undefined behavior that can crash the client process.

Affected Features / Interoperability: PHP `mysqlnd` driver (used by `mysqli`, `PDO_MySQL`). Downstream impact: client-side denial of service when connecting to a malicious/compromised server.

Source: https://github.com/php/php-src/security/advisories/GHSA-r6x9-5r99-36j7

Actions:

  • Fix: Apply PHP security update containing the `mysqlnd` fix (check distribution advisories).
  • Workaround: Avoid connecting to untrusted MySQL servers; use TLS with certificate validation to reduce risk of server impersonation.
  • Tradeoff: No significant tradeoff for patching; TLS validation may require certificate management.

Summary: pgPointcloud ≤1.2.5 contains a heap out-of-bounds read in dimensional patch WKB deserialization. Authenticated database users can supply crafted `pcpatch` values with attacker-controlled size fields to copy adjacent heap memory into stored patches for exfiltration or crash the PostgreSQL backend.

Affected Features / Interoperability: pgPointcloud extension (point cloud data type); WKB deserialization code path (`pc_bytes.c`). Downstream impact: memory disclosure (potential secrets/keys in heap), backend crash (DoS).

  • Workaround: Restrict `pcpatch` input to trusted sources; revoke extension usage from untrusted roles; consider disabling the extension if not required.
  • Tradeoff: Disabling the extension breaks point-cloud functionality; input restriction may limit legitimate GIS workflows.
PostgreSQLCVE-2026-100612CVSS 7.2 · HIGH

Summary: Capgo (capgo.app) ≤12.261.0 has an incomplete access-control fix for `public.sso_providers`. A migration installs a BEFORE UPDATE guard freezing only `dns_verified_at`, `domain`, `status`, `enforce_sso` — leaving `provider_id`, `metadata_url`, `attribute_mapping` writable. The table grants ALL to `anon`/`authenticated` roles; RLS policies constrain rows but not columns. An `org_admin` can PATCH `provider_id` via PostgREST to an IdP they control, then authenticate as the org owner, triggering account takeover and lockout of the legitimate owner. Requires target org to have active SSO and attacker to hold `org_admin`. No patched version available.

Affected Features / Interoperability: Capgo `sso_providers` table, PostgREST API, RLS policies. Downstream impact: vertical privilege escalation, account takeover, session invalidation for legitimate owner.

Source: https://github.com/Cap-go/capgo.app/security/advisories/GHSA-jpjp-v827-j4gc, https://www.vulncheck.com/advisories/capgo-sso-provider-id-authentication-bypass-via-incomplete-migration

Actions:

  • Fix: No patched version yet; monitor Capgo releases for a fix addressing column-level restrictions on `provider_id`.
  • Workaround: Revoke UPDATE on `sso_providers` from `anon`/`authenticated` roles; implement column-level privileges or a stricter RLS policy blocking `provider_id` changes; audit `org_admin` assignments.
  • Tradeoff: Revoking UPDATE may break legitimate SSO configuration workflows; column-level privileges require PostgreSQL 14+ and careful policy design.
PostgreSQLCVE-2026-97469CVSS 4.3 · MEDIUM

MongoDBCVE-2026-96749CVSS 8.4 · HIGH

Summary: An integer overflow in the BSON document encoding component of the MongoDB Python Driver's bundled native extension (≤4.18.1) occurs when encoding a single document from unusually large caller-supplied data. Size arithmetic uses a signed 32-bit type; the overflow guard has undefined behavior per C standard. An unprivileged party who can place a very large value into application-encoded data may cause an out-of-bounds write in the application process.

Affected Features / Interoperability: MongoDB Python Driver (`pymongo`) native extension BSON encoder. Downstream impact: potential remote code execution or process crash in applications encoding attacker-controlled data.

Source: https://github.com/mongodb/mongo-python-driver/blob/4.18.2/doc/changelog.rst, https://github.com/mongodb/mongo-python-driver/releases/tag/4.18.2, https://github.com/mongodb/mongo-python-driver/security/advisories/GHSA-v4x9-3549-crwv

Actions:

  • Fix: Upgrade MongoDB Python Driver to 4.18.2.
  • Workaround: Validate and limit size of user-supplied data before BSON encoding; run application with reduced privileges (e.g., container, non-root).
  • Tradeoff: Input size limits may reject legitimate large documents; privilege reduction is defense-in-depth with no functional tradeoff.

  • Tradeoff: Privilege restriction may complicate key management workflows; isolation increases operational overhead.

MongoDBCVE-2026-18710CVSS 6.5 · MEDIUM

Microsoft Azure — CVE-2026-84458 (CVSS UNSCORED )

Summary: Zammad’s “Automatic account link on initial logon” feature binds an incoming SSO identity to a local account by matching the email address provided by the identity provider without verifying that the provider actually confirmed ownership of that email. An attacker who controls any identity at a configured SSO provider (including Azure AD via Zammad’s multi-tenant Microsoft 365 /common app registration) can set that identity’s email to a victim’s address, authenticate, and log in as the victim, bypassing local password protection.
