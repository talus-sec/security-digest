Scoped Vulnerability Tracking

Database

The most urgent items are two PostgreSQL vulnerabilities (CVE-2026-6473 and CVE-2026-6477, both CVSS 8.8) that allow an unprivileged database user to achieve arbitrary code execution as the operating system user running the database via integer wraparound and a libpq stack-buffer overflow. Both affect all supported PostgreSQL versions prior to the May 2026 patch releases (18.4, 17.10, 16.14, 15.18, 14.23) and are directly relevant to the healthcare enterprise PostgreSQL fleet and the homelab Postgres/Vault PKI/mTLS stack. No CISA KEV entries are present in this dataset, so these highest-CVSS issues take top priority.

Formal Vulnerabilities

MySQLCVE-2026-59335CVSS 8.7 · HIGH

Summary: A case-sensitivity mismatch in Cloud Foundry UAA’s identity zone authorization check allows a remote authenticated attacker with only the `zones.write` authority to bypass restrictions and access the privileged system zone when UAA is backed by MySQL using its default case-insensitive collation. The attacker can overwrite the system zone’s JWT signing key, forge admin JWTs, and fully compromise UAA and any trusting Cloud Foundry deployment. PostgreSQL and HSQLDB backends are not affected.

Affected Features / Interoperability: Cloud Foundry UAA identity zone management when persisted to MySQL with default collation; impacts JWT-based authentication and authorization across the Cloud Foundry platform. Downstream integrations relying on UAA-issued tokens (e.g., service-to-service auth, SSO) would be compromised.

Source: https://www.cloudfoundry.org/blog/cve-2026-59335-uaa-case-insensitive-check-bypass/

Actions:

  • Fix: Upgrade UAA to a patched release (per Cloud Foundry advisory); ensure MySQL collation is case-sensitive or migrate to PostgreSQL/HSQLDB backend.
  • Workaround: Enforce case-sensitive collation on the MySQL schema (e.g., `utf8mb4_bin`) or restrict `zones.write` authority to trusted administrators only.
  • Tradeoff: Changing collation may affect existing applications that rely on case-insensitive comparisons; restricting authority may limit legitimate multi-tenancy operations.
MySQLCVE-2026-70724CVSS 7.5 · HIGH

Summary: An unauthenticated, network-accessible vulnerability in MySQL Cluster (HTTP interface) that requires human interaction (e.g., phishing) to exploit. Successful exploitation can lead to full takeover of the MySQL Cluster. Affected versions: 8.0.0–8.0.48, 8.4.0–8.4.11, 9.7.0–9.7.2.

Affected Features / Interoperability: MySQL Cluster management and HTTP endpoints; could impact cluster replication, data distribution, and any applications relying on Cluster’s high-availability features.

Source: https://www.oracle.com/security-alerts/cspuaug2026.html

Actions:

  • Fix: Apply the Oracle Critical Patch Update (August 2026) which includes patched versions for each affected series.
  • Workaround: Restrict network access to MySQL Cluster HTTP ports to trusted hosts only; disable HTTP interface if not required.
  • Tradeoff: Disabling HTTP interface may break cluster monitoring/management tools that depend on it.
PostgreSQLCVE-2026-6473CVSS 8.8 · HIGH

Summary: Integer wraparound in multiple PostgreSQL server features allows an unprivileged database user to cause an undersized allocation and out-of-bounds write, leading to arbitrary code execution as the OS user running the database. Triggered by passing gigabyte-scale user inputs to affected database functions.

Affected Features / Interoperability: Core server functions that handle large user inputs (exact functions not specified in advisory). Could impact any workload that processes large objects, bulk imports, or user-supplied data via SQL functions. Replication, logical decoding, and extensions that call into vulnerable code paths may also be affected.

Source: https://www.postgresql.org/support/security/CVE-2026-6473/, https://access.redhat.com/errata/RHSA-2026:22878, https://access.redhat.com/errata/RHSA-2026:26181, https://access.redhat.com/errata/RHSA-2026:26203, https://access.redhat.com/errata/RHSA-2026:26204

Actions:

  • Fix: Upgrade to PostgreSQL 18.4, 17.10, 16.14, 15.18, or 14.23 (or later).
  • Workaround: Limit maximum input sizes for user-supplied data to vulnerable functions (e.g., via application-layer validation or PostgreSQL `statement_timeout`/`max_allowed_packet` equivalents); restrict untrusted users from executing functions that accept large inputs.
  • Tradeoff: Input-size limits may break legitimate large-data workflows (e.g., bulk loading, GIS, scientific data). Function restrictions may require application changes.
PostgreSQLCVE-2026-6477CVSS 8.8 · HIGH

Summary: The libpq functions `lo_export()`, `lo_read()`, `lo_lseek64()`, and `lo_tell64()` use the unsafe `PQfn(..., result_is_int=0, ...)` which allows a malicious server superuser to overwrite a client stack buffer with an arbitrarily large response. This affects `psql`'s `\lo_export` command and `pg_dump`, enabling a compromised server to attack backup/admin clients.

Affected Features / Interoperability: Large object (LO) operations in libpq, `psql`, and `pg_dump`. Any client using these functions (including backup scripts, replication tools, and custom applications) is vulnerable when connecting to a malicious or compromised server.

Source: https://www.postgresql.org/support/security/CVE-2026-6477/, https://access.redhat.com/errata/RHSA-2026:21182, https://access.redhat.com/errata/RHSA-2026:22878, https://access.redhat.com/errata/RHSA-2026:26181, https://access.redhat.com/errata/RHSA-2026:26203

Actions:

  • Fix: Upgrade to PostgreSQL 18.4, 17.10, 16.14, 15.18, or 14.23 (or later) on both server and client sides.
  • Workaround: Avoid using large object functions (`lo_export`, `lo_read`, etc.) in scripts and backups; use `COPY` or other non-LO methods for data export. Ensure `pg_dump` is run only against trusted servers.
  • Tradeoff: Avoiding LO functions may require application/schema changes; running `pg_dump` only against trusted servers is standard practice but may complicate cross-environment backups.
PostgreSQLCVE-2026-59335CVSS 8.7 · HIGH

Summary: Identical to the MySQL entry above: a case-sensitivity bypass in Cloud Foundry UAA when backed by MySQL. The advisory explicitly states PostgreSQL backends are not affected. This entry appears in the PostgreSQL feed likely due to shared CVE tracking; no PostgreSQL-specific vulnerability exists.

Affected Features / Interoperability: None for PostgreSQL; the vulnerability is specific to MySQL-backed UAA deployments.

Source: https://www.cloudfoundry.org/blog/cve-2026-59335-uaa-case-insensitive-check-bypass/

Actions:

  • Fix: Not applicable to PostgreSQL.
  • Workaround: Not applicable.
  • Tradeoff: No significant tradeoff.
PostgreSQLCVE-2026-55765CVSS 8.5 · HIGH

Summary: CloudNativePG (PostgreSQL operator for Kubernetes) embedded cleartext role passwords in `ALTER ROLE`/`CREATE ROLE` statements prior to versions 1.28.4, 1.29.2, and 1.30.0. When `pg_stat_statements` is preloaded with `track_utility` enabled, an untrusted tenant with `pg_monitor` or `pg_read_all_stats` can read those passwords, reconnect as superuser via TCP, and execute OS commands via `COPY ... FROM PROGRAM`. Clusters using SCRAM-SHA-256 verifiers in managed-role Secrets are not affected.

Affected Features / Interoperability: CloudNativePG-managed PostgreSQL clusters in Kubernetes; impacts secret handling, role management, and `pg_stat_statements` visibility. Downstream: any Kubernetes-hosted PostgreSQL workloads using CloudNativePG with password-based authentication and `pg_stat_statements` enabled.

Source: https://github.com/cloudnative-pg/cloudnative-pg/commit/2f0342747e1f160425b9d51753c0069b0d6117d5, https://github.com/cloudnative-pg/cloudnative-pg/commit/3cd5af5d388c26758acf13c19ea806b4bcebb3fe, https://github.com/cloudnative-pg/cloudnative-pg/commit/9a13573dbe3d78721b7ea92141e6d2324a2c0ef0, https://github.com/cloudnative-pg/cloudnative-pg/pull/10724, https://github.com/cloudnative-pg/cloudnative-pg/releases/tag/v1.28.4

Actions:

  • Fix: Upgrade CloudNativePG to 1.28.4, 1.29.2, or 1.30.0+.
  • Workaround: Disable `track_utility` in `pg_stat_statements`; migrate managed roles to SCRAM-SHA-256 verifiers; restrict `pg_monitor`/`pg_read_all_stats` grants to trusted roles only.
  • Tradeoff: Disabling `track_utility` loses visibility into utility commands; SCRAM migration requires client driver support and password rotation.
PostgreSQLCVE-2026-76635CVSS 7.2 · HIGH

Summary: baserCMS before 5.3.0 has a SQL injection in `BcDatabaseService.php` allowing authenticated administrators to inject table names and configuration values into SQL statements (sequence update, CSV export, table management). Combined with a backup-restore code injection flaw, attackers can plant malicious table names and extract data via error-based SQL injection against the PostgreSQL backend.

Affected Features / Interoperability: baserCMS admin panel features: sequence management, CSV export, table management, and backup/restore. Impacts any PostgreSQL database used by baserCMS.

Source: https://github.com/baserproject/basercms/releases/tag/5.3.0, https://github.com/baserproject/basercms/security/advisories/GHSA-cg65-f2m7-9fqj, https://www.vulncheck.com/advisories/basercms-sql-injection-and-code-injection-via-bcdatabaseservice-php

Actions:

  • Fix: Upgrade baserCMS to 5.3.0 or later.
  • Workaround: Restrict admin panel access to trusted networks; disable backup/restore functionality if not needed; monitor for anomalous SQL errors.
  • Tradeoff: Disabling admin features reduces CMS manageability; network restrictions may hinder legitimate remote administration.
PostgreSQLCVE-2026-6478CVSS 6.5 · MEDIUM

Summary: A covert timing channel in the comparison of MD5-hashed passwords during PostgreSQL authentication allows credential recovery. Does not affect `scram-sha-256` (default in all supported releases). Only impacts databases with MD5 passwords carried over from upgrades from PostgreSQL 13 or earlier.

Affected Features / Interoperability: PostgreSQL authentication subsystem for MD5-hashed passwords. Client drivers and applications using password authentication with legacy MD5 hashes.

Source: https://www.postgresql.org/support/security/CVE-2026-6478/, https://access.redhat.com/errata/RHSA-2026:21182, https://access.redhat.com/errata/RHSA-2026:22878, https://access.redhat.com/errata/RHSA-2026:26181, https://access.redhat.com/errata/RHSA-2026:26203

Actions:

  • Fix: Upgrade to PostgreSQL 18.4, 17.10, 16.14, 15.18, or 14.23 (or later).
  • Workaround: Rotate all MD5 passwords to SCRAM-SHA-256 (`ALTER ROLE ... PASSWORD '...'` with `password_encryption = 'scram-sha-256'`); disable MD5 authentication in `pg_hba.conf`.
  • Tradeoff: Password rotation requires coordinated client updates; disabling MD5 may break older clients that don’t support SCRAM.
Oracle DatabaseCVE-2021-2351CVSS 8.3 · HIGH

Summary: Vulnerability in the Advanced Networking Option (ANO) of Oracle Database Server (versions 12.1.0.2, 12.2.0.1, 19c). An unauthenticated attacker with network access via Oracle Net can compromise ANO, requiring human interaction. Successful attacks may significantly impact additional products and result in takeover of ANO. The July 2021 CPU introduced Native Network Encryption changes to mitigate this and prevent weaker ciphers.

Affected Features / Interoperability: Oracle Advanced Networking Option (encryption/integrity for Oracle Net). Downstream: any database links, client connections, or middleware relying on ANO for network security.

Source: http://packetstormsecurity.com/files/165255/Oracle-Database-Protection-Mechanism-Bypass.html, http://packetstormsecurity.com/files/165258/Oracle-Database-Weak-NNE-Integrity-Key-Derivation.html, http://seclists.org/fulldisclosure/2021/Dec/19, http://seclists.org/fulldisclosure/2021/Dec/20, https://www.oracle.com/security-alerts/cpuapr2022.html

Actions:

  • Fix: Apply the July 2021 Critical Patch Update (or later) for the affected versions; review Doc ID 2791571.1 for Native Network Encryption changes.
  • Workaround: Disable ANO if not required; enforce strong cipher suites via `sqlnet.ora`; restrict Oracle Net listener exposure to trusted networks.
  • Tradeoff: Disabling ANO removes network encryption/integrity; cipher restrictions may break compatibility with older clients.
