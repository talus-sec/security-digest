Scoped Vulnerability Tracking

Database

The single most urgent item this period is CVE-2019-1068 in Microsoft SQL Server, a CISA KEV-confirmed actively exploited vulnerability with an expired remediation due date of August 29, 2026. While several CVSS-critical vulnerabilities appear in the database landscape—including an ArcadeDB authentication bypass (CVSS 9.8) and hardcoded credential exposures in PostgreSQL tooling (CVSS 9.8)—CISA's confirmed exploitation classification takes precedence over theoretical severity scores. Immediate action is required for the SQL Server entry; the remaining entries below are sorted by confirmed-exploitation status first, then CVSS descending.

Formal Vulnerabilities

MySQLCVE-2026-55215CVSS 7.5 · HIGH

Summary: MariaDB Connector/Node.js (versions prior to 3.3.3, 3.4.6, 3.5.3) transmits database credentials to the server before completing TLS certificate validation when SSL is enabled without a pinned CA or server certificate. An active man-in-the-middle attacker can present a self-signed certificate, capture the plaintext password, and authenticate directly—even though the connector subsequently rejects the server and closes the connection. This affects any application using the Node.js connector with SSL enabled but no certificate pinning.

Affected Features / Interoperability: TLS/SSL handshake and authentication handshake in the MariaDB Connector/Node.js library. Downstream impact: any application using this connector to connect to MariaDB or MySQL with `ssl` enabled but without pinned certificates or strict CA validation.

Source: https://github.com/mariadb-corporation/mariadb-connector-nodejs/releases/tag/3.3.3

Actions:

  • Fix: Upgrade to MariaDB Connector/Node.js 3.3.3, 3.4.6, or 3.5.3.
  • Workaround: Enforce strict TLS certificate validation by pinning the server certificate or CA (`ca` option in connection string) and disabling fallback to insecure modes.
  • Tradeoff: Requires obtaining and maintaining the server's TLS certificate or CA chain; certificate rotation requires connector config updates.
MySQLCVE-2026-75133CVSS 7.5 · HIGH

Summary: The Keep Backup Daily WordPress plugin (versions prior to 2.1.4) exposes a cron endpoint (`kbd_cron_process`) without authentication, allowing unauthenticated attackers to trigger full MySQL database dumps. Attackers can predict the partially randomized backup filename based on the database name, a limited random range, and the Unix timestamp, then download the backup from the publicly accessible uploads directory.

Affected Features / Interoperability: The plugin's backup creation and storage mechanism; any WordPress instance using this plugin with MySQL as its backend database.

Source: https://www.vulncheck.com/advisories/keep-backup-daily-wordpress-plugin-sensitive-information-exposure-via-kbd-cron-process

Actions:

  • Fix: Upgrade to Keep Backup Daily plugin version 2.1.4.
  • Workaround: Restrict web access to the `wp-content/uploads/` directory and the plugin's cron endpoint via web server configuration (e.g., deny all in nginx/apache); disable the plugin if not actively needed.
  • Tradeoff: Blocking uploads directory may break legitimate plugins that serve user content from that path.
MySQLCVE-2026-39931CVSS 7.2 · HIGH

Summary: OpenEMR through version 8.2.0 contains an authenticated SQL injection vulnerability in the backup configuration import feature. Administrators with admin or super ACL privileges can upload a crafted SQL file at `form_step=202` in `backup.php`, and the application passes unfiltered input to `shell_exec` invoking the `mysql` CLI. Attackers can extract credential hashes, modify access controls, inject backdoor accounts, or write arbitrary files if MySQL FILE privileges and `secure_file_priv` settings permit.

Affected Features / Interoperability: OpenEMR's backup import functionality and MySQL CLI interaction; affects OpenEMR deployments using MySQL as the backend database.

Source: https://jivasecurity.com/writeups/openemr-backup-import-arbitrary-sql-cve-2026-39931

Actions:

  • Fix: No specific patched version is cited in available data; monitor OpenEMR's security advisories for version 8.2.1 or later.
  • Workaround: Restrict the `backup.php` import feature to super-admin accounts only; consider disabling the feature entirely if not required for operations; enforce least-privilege MySQL user for the application with FILE privileges revoked.
  • Tradeoff: Disabling backup import may disrupt legitimate administrative workflows; restricting to super-admin limits delegation.
MySQLCVE-2026-55855CVSS 6.5 · MEDIUM

Summary: MariaDB Connector/Node.js (versions prior to 3.2.4, 3.3.3, 3.4.6, 3.5.3) permits SQL injection when attacker-controlled Buffer parameters are escaped client-side under certain Asian character sets (big5, gbk, sjis, cp932, gb18030). The connector's byte-escaping logic bypasses charset-aware validation, allowing an attacker-controlled lead byte to consume a backslash as a multibyte trail byte and leave the following quote unescaped, terminating the string and enabling arbitrary SQL. The default `utf8mb4` charset and prepared statement parameters are not affected.

Affected Features / Interoperability: SQL parameter escaping under legacy Asian character sets in MariaDB Connector/Node.js; impacts applications that use these charsets and pass attacker-influenced data as parameters.

Source: https://github.com/mariadb-corporation/mariadb-connector-nodejs/releases/tag/3.2.4

Actions:

  • Fix: Upgrade to MariaDB Connector/Node.js 3.2.4, 3.3.3, 3.4.6, or 3.5.3.
  • Workaround: Avoid using affected character sets (big5, gbk, sjis, cp932, gb18030) when connecting; migrate to `utf8mb4`.
  • Tradeoff: Migration from legacy charsets may require schema changes and application testing for encoding edge cases.

MySQLCVE-2026-55854CVSS 5.9 · MEDIUM

Summary: MariaDB Connector/Node.js (versions prior to 3.2.4, 3.3.3, 3.4.6, 3.5.3) can disclose an account password when PAM dialog authentication is negotiated over an insecure transport. With default `sslMode=DISABLE` and `restrictedAuth=null` settings, a hostile or on-path server can request dialog authentication over plain TCP, causing the connector to transmit the password in cleartext. Proper TLS verification or local Unix sockets prevent this path, but fingerprint-only validation is insufficient.

Affected Features / Interoperability: PAM (Pluggable Authentication Modules) authentication in MariaDB Connector/Node.js; impacts deployments using PAM auth with the default SSL disabled.

Source: https://github.com/mariadb-corporation/mariadb-connector-nodejs/releases/tag/3.2.4

Actions:

  • Fix: Upgrade to MariaDB Connector/Node.js 3.2.4, 3.3.3, 3.4.6, or 3.5.3.
  • Workaround: Enforce TLS for connections using PAM auth (`sslMode=VERIFY_CA` or `VERIFY_IDENTITY`); avoid `sslMode=DISABLE` with PAM.
  • Tradeoff: TLS enforcement may require certificate infrastructure changes; additional latency from TLS handshake.
MySQLCVE-2026-55856CVSS 5.9 · MEDIUM

Summary: MariaDB Connector/J (versions prior to 2.7.14, 3.3.5, 3.4.3, 3.5.9) can be susceptible to credential interception during the initial TLS handshake when connecting with `sslMode=verify-full` or `sslMode=verify-ca` and a password, but without configuring `serverSslCert` or a trustStore. The connector's initial-handshake path does not enforce certificate fingerprint validation, allowing an active man-in-the-middle to present a self-signed certificate, claim to be the database server, and receive the password via `mysql_clear_password` before the connection is rejected.

Affected Features / Interoperability: Initial TLS handshake and authentication in MariaDB Connector/J; impacts Java applications using these SSL modes without explicit certificate pinning.

Source: https://github.com/mariadb-corporation/mariadb-connector-j/security/advisories/GHSA-g9jj-cgmh-9f38

Actions:

  • Fix: Upgrade to MariaDB Connector/J 2.7.14, 3.3.5, 3.4.3, or 3.5.9.
  • Workaround: Configure `serverSslCert` or a trustStore containing the server's CA; enable `sslMode=VERIFY_IDENTITY` and ensure `restrictedAuth` is set appropriately.
  • Tradeoff: Requires maintaining server certificates or CA chains; additional configuration complexity.
MySQLCVE-2026-55857CVSS 5.9 · MEDIUM

Summary: MariaDB Connector/J (versions prior to 2.7.14, 3.3.5, 3.4.3, 3.5.9) allows PAM dialog authentication to transmit the account password over an insecure connection. The `mysql_clear_password` plugin is protected by secure-transport requirements, but the sibling PAM dialog handler does not inherit this protection, defaulting to no secure-transport requirement. With default `sslMode=DISABLE` and `restrictedAuth=null`, a hostile server can request dialog auth over plain TCP and receive the plaintext password.

Affected Features / Interoperability: PAM dialog authentication path in MariaDB Connector/J; impacts deployments using PAM auth without TLS enforcement.

Source: https://github.com/mariadb-corporation/mariadb-connector-j/security/advisories/GHSA-qxvw-fvwx-5cp7

Actions:

  • Fix: Upgrade to MariaDB Connector/J 2.7.14, 3.3.5, 3.4.3, or 3.5.9.
  • Workaround: Enforce TLS for connections using PAM auth; avoid `sslMode=DISABLE`.
  • Tradeoff: Same as CVE-2026-55854—may require certificate infrastructure changes.
MySQLCVE-2026-55858CVSS 5.9 · MEDIUM

Summary: MariaDB Connector/J (versions prior to 2.7.14, 3.3.5, 3.4.3, 3.5.9) encodes and decodes protocol text assuming the connection character set is UTF-8. The server can announce a mid-session change to `character_set_client` (e.g., via `SET NAMES`, stored routines, triggers, or a hostile server), causing the driver to continue reading/writing UTF-8 while the server interprets the same bytes under a different encoding. This leads to silent data corruption and can defeat byte-wise quoting or escaping. The fix rejects any non-UTF-8 charset after initialization with a SQLException.

Affected Features / Interoperability: Character set handling in MariaDB Connector/J protocol; impacts applications where server-side configuration or attacker-controlled sessions can alter the character set mid-session.

Source: https://github.com/mariadb-corporation/mariadb-connector-j/releases/tag/2.7.14

Actions:

  • Fix: Upgrade to MariaDB Connector/J 2.7.14, 3.3.5, 3.4.3, or 3.5.9.
  • Workaround: Enforce `character_set_client` at the server level via `init_connect` or configuration to prevent mid-session changes; avoid granting attackers the ability to execute arbitrary SQL.
  • Tradeoff: Server-level restrictions may break legitimate applications that legitimately change character sets; driver upgrade is the cleaner fix.
MySQLCVE-2026-55859CVSS 5.9 · MEDIUM

Summary: MariaDB Connector/R2DBC (versions prior to 1.4.1) has the same charset-confusion vulnerability as CVE-2026-55858, but in the R2DBC non-blocking driver for Java. A server can announce a mid-session character set change via OK-packet session-state tracking, causing silent data corruption when the driver continues using UTF-8 while the server interprets bytes under a different encoding. The fix rejects non-UTF-8 character sets after initialization with an exception.

Affected Features / Interoperability: Character set handling in the R2DBC driver for MariaDB and MySQL; impacts reactive/non-blocking Java applications using this driver.

Source: https://github.com/mariadb-corporation/mariadb-connector-r2dbc/security/advisories/GHSA-5rqc-86vf-g8r2

Actions:

  • Fix: Upgrade to MariaDB Connector/R2DBC 1.4.1.
  • Workaround: Prevent mid-session character set changes via server configuration or access controls as with CVE-2026-55858.
  • Tradeoff: Same as CVE-2026-55858—driver upgrade is preferred.

Summary: `openssl_encrypt` versions prior to 1.4.0 contain hardcoded database credentials in standalone server configuration files. Attackers on the same network can use these well-known default credentials to access PostgreSQL databases directly and retrieve sensitive data. This is a pre-configured credential exposure rather than a运行时 vulnerability.

Affected Features / Interoperability: Standalone server configuration files in `openssl_encrypt`; impacts any PostgreSQL database deployed alongside or managed by affected versions of this software.

  • Fix: Upgrade `openssl_encrypt` to version 1.4.0 or later.
  • Workaround: Immediately rotate any credentials that may have been present in configuration files; audit access logs for unauthorized access using default credentials.
  • Tradeoff: Credential rotation requires updating all dependent configurations; no functionality degradation.

Summary: baserCMS before version 5.3.0 has a SQL injection vulnerability in `BcDatabaseService.php` that allows authenticated administrators to inject attacker-controlled table names and configuration values directly into SQL statements. Attackers can chain this with a backup restore code injection flaw (PHP code outside class definitions in schema files executes unconditionally) to plant malicious table names and trigger error-based SQL injection against the PostgreSQL backend, retrieving database version, schema contents, and arbitrary data.

Affected Features / Interoperability: baserCMS database service layer; impacts any baserCMS deployment using PostgreSQL as its backend.

Source: https://github.com/baserproject/basercms/security/advisories/GHSA-cg65-f2m7-9fqj

  • Fix: Upgrade baserCMS to version 5.3.0.
  • Workaround: Restrict administrator access to trusted users only; consider disabling the backup restore feature if not operationally critical.
  • Tradeoff: Limiting administrator access may disrupt workflows; disabling backup restore limits recovery options.
PostgreSQLCVE-2026-70635CVSS 7.1 · HIGH

Summary: TimescaleDB through version 2.29.1 has an out-of-bounds read vulnerability in bulk text dictionary decompression. Authenticated attackers with direct DML access to a non-frozen physical compressed hypertable can supply a crafted Simple8b selector-11 value that bypasses index validation, causing an out-of-bounds read before the base of the live offsets array. This can result in incorrect aggregation output, backend `SIGSEGV`, or PostgreSQL crash recovery depending on build configuration.

Affected Features / Interoperability: TimescaleDB compressed hypertable operations; impacts TimescaleDB deployments using physical compression on hypertables with the Arrow dictionary-index type.

Source: https://github.com/timescale/timescaledb/pull/10360

Actions:

  • Fix: Upgrade TimescaleDB to the version containing commit `517c13e` (verify with vendor); monitor Timescale security advisories.
  • Workaround: Avoid direct DML on compressed hypertables for untrusted users; disable the VectorAgg feature if not required; ensure `max_worker_processes` and recovery configurations are set to handle potential crashes.
  • Tradeoff: Restricting DML on compressed hypertables may disrupt legitimate analytics workloads.

PostgreSQLCVE-2026-76212CVSS 5.3 · MEDIUM
