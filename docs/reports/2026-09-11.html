Scoped Vulnerability Tracking

Database

The most urgent item in today's digest is CVE-2026-87911 (PostgreSQL ecosystem, CVSS 9.6 CRITICAL): an OS command injection flaw in Amazon's `awslabs/postgres-mcp-server` that allows an unauthenticated attacker to execute operating system commands on a self-managed PostgreSQL host by injecting a crafted `COPY ... TO PROGRAM` statement into MCP server content. With a CVSS of 9.6 and no CISA KEV entry to compete against, this is the highest-severity confirmed vulnerability affecting database infrastructure this cycle. No KEV-confirmed entries were present in today's data, so the highest CVSS score determines priority.

Formal Vulnerabilities

MySQLCVE-2026-86213CVSS 7.3 · HIGH

Summary: A SQL injection vulnerability exists in the `mysqli_query` function of the `Front-end/university.php` file in the Mstfakts College-Management-System's Search Handler. Manipulation of the `book_name` or `book_author` arguments enables remote SQL injection. The exploit has been made public, and the project uses a rolling release system, so no version-specific patch information is disclosed.

Affected Features / Interoperability: The Search Handler component and its `mysqli_query` function are directly impacted. Any downstream functionality relying on the search feature—such as university catalog queries or book lookups—could be compromised. No specific interoperability impacts (e.g., replication, client drivers) are documented in the raw data.

Source:

  • https://github.com/Mstfakts/College-Management-System/
  • https://github.com/Mstfakts/College-Management-System/issues/5
  • https://vuldb.com/cve/CVE-2026-86213
  • https://vuldb.com/submit/897249
  • https://vuldb.com/vuln/399349

Actions:

  • Fix: Not disclosed. The project uses a rolling release system and has not responded to the initial issue report.
  • Workaround: Implement strict input validation and parameterized queries for the `book_name` and `book_author` parameters in the Search Handler.
  • Tradeoff: Strict input sanitization may break legitimate search queries containing special characters; parameterized queries require code changes to the application layer.

PostgreSQLCVE-2026-87911CVSS 9.6 · CRITICALActively exploited · CISA KEV

Summary: An OS command injection weakness exists in the read-only enforcement of the SQL validation component in Amazon `awslabs/postgres-mcp-server` before version 1.1.7. An unauthenticated actor can execute operating system commands on the host of a self-managed PostgreSQL server by placing a crafted `COPY ... TO PROGRAM` statement into content processed when an authenticated user interacts with the MCP server in its default read-only mode.

Affected Features / Interoperability: The `postgres-mcp-server` component and its SQL validation/read-only enforcement are impacted. The `COPY ... TO PROGRAM` PostgreSQL feature is the attack vector. Downstream integrations relying on the MCP server for PostgreSQL access—including AI tooling, automation pipelines, and any client connecting through the MCP layer—could be compromised. The vulnerability bypasses the intended read-only mode of the MCP server.

Source:

  • https://aws.amazon.com/security/security-bulletins/2026-104-aws/
  • https://github.com/awslabs/mcp/security/advisories/GHSA-fph8-pg5w-78fv
  • https://pypi.org/project/awslabs.postgres-mcp-server/1.1.7/

Actions:

  • Fix: Upgrade to version 1.1.7 or later of `awslabs/postgres-mcp-server`.
  • Workaround: If immediate upgrade is not possible, restrict MCP server access to trusted networks only, disable or audit `COPY ... TO PROGRAM` usage on the PostgreSQL server, and enforce strict input validation on all content processed by the MCP server.
  • Tradeoff: Disabling `COPY ... TO PROGRAM` removes the ability to execute server-side programs via PostgreSQL SQL commands, which may break legitimate administrative automation workflows that rely on this feature.

PostgreSQLCVE-2026-48031CVSS 9.1 · CRITICAL

Summary: The `go-base` Go RESTful API boilerplate template, backed by PostgreSQL, hardcodes its JWT signing secret to the known string `"random"` in versions prior to 2026-05-18. Any attacker who reads the public repository can forge JWT tokens for arbitrary users, including admin roles, completely bypassing authentication on all protected endpoints. The secret is set in both the `dev.env` template and a programmatic fallback in `cmd/serve.go`, meaning the application uses it even when no `.env` file is present.

Affected Features / Interoperability: JWT-based authentication in `go-base` applications backed by PostgreSQL is compromised. All protected API endpoints are accessible with forged tokens. The original mitigation in `auth/jwt/tokenauth.go` only caught the exact string `"random"`, allowing other weak secrets through. The replacement in-memory key was not persisted, invalidating all tokens on every restart and causing a denial-of-service condition.

Source:

  • https://github.com/dhax/go-base/commit/cc82b9740fa6b08e0fad409cd4b418e240dd0e00
  • https://github.com/dhax/go-base/pull/31
  • https://github.com/dhax/go-base/security/advisories/GHSA-mqq6-462x-jxmm

Actions:

  • Fix: Upgrade to version 2026-05-18 or later of `go-base`.
  • Workaround: If an immediate upgrade is not possible, rotate all JWT signing secrets to cryptographically strong random values, remove the hardcoded `"random"` fallback, and ensure a persistent `.env` file is always present with a strong secret.
  • Tradeoff: The original in-memory key workaround caused token invalidation on every restart (DoS). A proper fix requires persistent secret management; until then, any interim workaround that rotates secrets will invalidate existing sessions.

PostgreSQLCVE-2026-87016CVSS 8.1 · HIGH

Summary: In Open WebUI versions 0.6.41 through 0.11.1, the `get_user_by_oauth_sub` and `get_user_by_scim_external_id` functions in `backend/open_webui/models/users.py` used JSON contains matching that compiled to SQL LIKE substring matching on SQLite. An OAuth subject containing percent or underscore wildcard characters could resolve to a different stored identity, potentially selecting an administrator account and issuing the attacker that account's session. PostgreSQL deployments were explicitly not affected by this vulnerability.

Affected Features / Interoperability: Open WebUI's OAuth and SCIM authentication flows on SQLite-backed deployments are impacted. The vulnerability allows identity confusion via wildcard characters in OAuth subject claims. PostgreSQL deployments are not affected. Downstream functionality such as AI platform access control and user session management could be bypassed on affected SQLite deployments.

Source:

  • https://github.com/open-webui/open-webui/commit/73c1f5806aeb6345dad5de8f5aa26d1f3d0bef80
  • https://github.com/open-webui/open-webui/pull/28624
  • https://github.com/open-webui/open-webui/releases/tag/v0.11.1
  • https://github.com/open-webui/open-webui/security/advisories/GHSA-wpmr-8h3q-fwj7

  • Fix: Upgrade to Open WebUI version 0.11.1 or later.
  • Workaround: Not specified in the available data. As an interim measure, validate and sanitize OAuth subject claims for wildcard characters before processing.
  • Tradeoff: Sanitizing wildcard characters in OAuth subjects may break legitimate identity providers that use such characters in subject claims.

PostgreSQLCVE-2026-42198CVSS 7.5 · HIGH

Summary: The `pgjdbc` open-source PostgreSQL JDBC Driver (versions 42.2.0 through before 42.7.11) is vulnerable to a client-side denial of service during SCRAM-SHA-256 authentication. A malicious server can instruct the driver to perform SCRAM authentication with a very large iteration count, causing the client to spend an unbounded amount of CPU time inside PBKDF2 before authentication can fail. A single attempt ties up a CPU core, and repeated or concurrent attempts can exhaust client CPU and wedge connection pools. The `loginTimeout` setting did not fully mitigate this problem, as the worker thread could continue burning CPU even after the timeout expired.

Affected Features / Interoperability: The `pgjdbc` JDBC Driver's SCRAM-SHA-256 authentication path is impacted. Any Java application using `pgjdbc` to connect to a PostgreSQL server is vulnerable if connecting to a malicious or compromised server. Connection pools in affected Java applications could be exhausted, leading to service disruption. Downstream integrations relying on JDBC connections—such as Java-based data pipelines, application servers, and ETL tools—could be affected.

Source:

  • https://github.com/pgjdbc/pgjdbc/releases/tag/REL42.7.11
  • https://github.com/pgjdbc/pgjdbc/security/advisories/GHSA-98qh-xjc8-98pq
  • https://access.redhat.com/errata/RHSA-2026:19098
  • https://access.redhat.com/errata/RHSA-2026:22304
  • https://access.redhat.com/errata/RHSA-2026:24348

Actions:

  • Fix: Upgrade to `pgjdbc` version 42.7.11 or later.
  • Workaround: If an immediate upgrade is not possible, restrict PostgreSQL server connections to trusted sources only, and configure connection pool limits to cap the number of concurrent authentication attempts that could be exploited.
  • Tradeoff: Restricting server connections to trusted sources limits flexibility in multi-tenant or federated database environments. Connection pool limits may reduce overall application throughput under high load.

MongoDBCVE-2026-88023CVSS 8.3 · HIGH

Summary: Improper neutralization of special elements in data query logic in the GridFS component of the MongoDB PHP Library allows a caller-supplied structured file identifier to be interpreted as a query condition rather than as a literal identifier. An authenticated user who can influence the identifier passed by an affected application may obtain stored file content beyond the intended target or cause all GridFS file chunks in the affected bucket to be removed, rendering stored file content unreadable. The affected rename operation may also rename a stored file other than the intended target.

Affected Features / Interoperability: The GridFS component of the MongoDB PHP Library is impacted. File storage and retrieval operations via GridFS in PHP applications are compromised. Downstream integrations relying on GridFS for file storage—such as document management systems, media libraries, and content repositories—could experience data leakage or data loss. The rename operation may also corrupt file organization.

Source:

  • https://jira.mongodb.org/browse/PHPLIB-1929

Actions:

  • Fix: Not specified in the available data. Check the MongoDB PHP Library release notes for a patched version.
  • Workaround: Validate and sanitize all file identifiers passed to GridFS operations to ensure they are treated as literal identifiers, not query conditions. Implement strict input validation on any user-supplied identifiers used in GridFS API calls.
  • Tradeoff: Strict identifier validation may break applications that rely on complex or structured file identifiers. Additional input sanitization adds processing overhead.

Summary: Improper neutralization of special elements in data query logic in the GridFS component of the MongoDB Java Driver allows a caller-supplied structured file identifier to be interpreted as a query condition rather than as a literal identifier. An authenticated user who can influence the identifier passed by an affected application may obtain stored file content beyond the intended target or cause all GridFS file chunks in the affected bucket to be removed, rendering stored file content unreadable. The affected rename operation may also rename a stored file other than the intended target.

Affected Features / Interoperability: The GridFS component of the MongoDB Java Driver is impacted. File storage and retrieval operations via GridFS in Java applications are compromised. Downstream integrations relying on GridFS for file storage in Java-based enterprise applications could experience data leakage or data loss. The rename operation may also corrupt file organization.

Source:

  • https://jira.mongodb.org/browse/JAVA-6283

Actions:

  • Fix: Not specified in the available data. Check the MongoDB Java Driver release notes for a patched version.
  • Workaround: Validate and sanitize all file identifiers passed to GridFS operations to ensure they are treated as literal identifiers. Implement strict input validation on user-supplied identifiers used in GridFS API calls.
  • Tradeoff: Strict identifier validation may break applications that rely on complex or structured file identifiers. Additional input sanitization adds processing overhead.
