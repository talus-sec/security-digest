# Security Digest — 2026-09-19

## Database

The most urgent threat is CVE-2026-85878 affecting Azure Database for PostgreSQL, which allows unauthenticated attackers to elevate privileges across the network, posing a critical risk to database administration and data integrity. This CISA KEV-confirmed entry demands immediate remediation to prevent unauthorized access and potential system compromise.

## Cloud Security

The most urgent item today is **CVE-2026-61682** (CVSS 9.9 CRITICAL) in the kcp Kubernetes-like control plane, where the front-proxy fails to strip identity headers before forwarding to shards, enabling any authenticated tenant to impersonate system masters and bypass authorization across workspaces. While no CISA KEV-confirmed entries appear in this digest's dataset, this 9.9-score critical vulnerability represents the highest theoretical severity and is actively exploitable by any authenticated tenant in affected deployments. Secondary high-priority items include CVE-2026-75156 (CVSS 9.1, Azure AD OAuth token validation bypass in Apache Airflow FAB) and two Docker-related high-severity flaws in ToolHive and Pelican Panel.

### Formal Vulnerabilities

#### [Microsoft Azure] — CVE-2026-75156 (CVSS 9.1) [CRITICAL]
**Summary:** Apache Airflow FAB provider versions 3.7.3 through 3.8.0 do not validate the issuer or audience of Azure AD `id_token`s during OAuth login. Because signing keys are fetched from Microsoft's multi-tenant JWKS endpoint, an attacker who can register an Azure tenant can mint a valid `id_token` in their own tenant and authenticate to the Airflow UI with no prior access. The incomplete fix for CVE-2026-59243 only added signature verification, not issuer/audience checks, so operators who applied that fix are still affected.

**Affected Features / Interoperability:** Airflow's FAB auth manager when configured with Azure AD as an OAuth provider. Downstream impacts include unauthorized access to the Airflow UI, potential privilege escalation via role assignments read from the attacker-controlled token, and compromise of any workflow or DAG executed under the authenticated session. Client drivers and extensions relying on the FAB auth manager for Azure AD SSO would be affected.

**Source:**
- https://github.com/apache/airflow/pull/71735
- https://lists.apache.org/thread/n3l6z4jfdxj4p0t8l7m6olkq6xsc6f76
- https://www.cve.org/CVERecord?id=CVE-2026-59243

**Actions:**
- Fix: Upgrade to `apache-airflow-providers-fab` 3.8.1 or later.
- Workaround: If immediate upgrade is not possible, restrict Azure AD OAuth to single-tenant mode and validate issuer/audience at the application level before trusting any token.
- Tradeoff: Single-tenant mode limits flexibility for multi-tenant deployments and may break cross-tenant integrations.

#### [Kubernetes] — CVE-2026-61682 (CVSS 9.9) [CRITICAL]
**Summary:** kcp is a Kubernetes-like control plane for form-factors beyond standard Kubernetes. Prior to versions 0.31.4 and 0.32.2, the kcp front-proxy does not remove inbound X-Remote-User, X-Remote-Group, or X-Remote-Extra-* identity headers before forwarding requests to shards. Any authenticated tenant can inject X-Remote-Group: system:masters or other privileged identity headers, and the shard trusts these as authenticated assertions. This enables cross-workspace impersonation, authorization bypass, and arbitrary reading, writing, or deletion of resources, secrets, RBAC data, APIExports, APIBindings, and LogicalClusters.

**Affected Features / Interoperability:** kcp front-proxy and all shards relying on forwarded identity headers for authorization. Downstream impacts include complete cluster takeover by any authenticated tenant, cross-workspace resource access, RBAC bypass, and potential lateral movement across all workspaces managed by the kcp control plane. Integrations depending on kcp's multi-tenancy isolation (e.g., multi-tenant Kubernetes services, cross-workspace APIs) are fully compromised.

**Source:**
- https://github.com/kcp-dev/kcp/commit/7437cdcfec8f927d1a9bf1b2dd1e075d038e27ca
- https://github.com/kcp-dev/kcp/commit/f913ee890fb2fd9fa78e50c43474b078bfb6aeff
- https://github.com/kcp-dev/kcp/releases/tag/v0.31.4
- https://github.com/kcp-dev/kcp/releases/tag/v0.32.2
- https://github.com/kcp-dev/kcp/security/advisories/GHSA-c8w2-fgvx-vhv4

**Actions:**
- Fix: Upgrade to kcp version 0.31.4 or 0.32.2 (depending on your branch).
- Workaround: If immediate upgrade is not possible, configure the front-proxy to strip all X-Remote-* headers before forwarding requests to shards, and enforce shard-side identity validation independent of forwarded headers.
- Tradeoff: Stripping headers may break legitimate authentication flows if the system relies on them; a full upgrade is strongly preferred.

- Fix: Upgrade to Contour v1.33.5.

- Tradeoff: Removing fallback certificates means clients without SNI will not be served; removing jwtProviders disables JWT authentication for those routes.
