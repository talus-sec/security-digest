# Security Digest — 2026-08-25

## Database

This cycle's database security landscape is dominated by two high-severity issues in PostgreSQL's pglogical extension (CVE-2026-50736 and CVE-2026-50737, both CVSS 7.5) that enable privilege escalation from a limited pglogical role to full superuser, combined with a SQL injection vector in the popular TypeORM library (CVE-2026-76848, CVSS 7.5) that could expose data beyond an application's intended access scope. For MySQL, the most actionable item is a cross-site scripting flaw in Adminer (CVE-2026-56704, CVSS 6.1) where a rogue MySQL server can weaponize crafted version strings against Adminer clients. No CISA KEV-confirmed active exploitation entries are present this cycle.

### Formal Vulnerabilities

#### MySQL — CVE-2026-56704 (CVSS 6.1 MEDIUM)
**Summary:** Adminer before version 5.4.3 is vulnerable to a stored cross-site scripting (XSS) attack via the MySQL server version string. When a client connects through Adminer to a MySQL server controlled by an attacker, that server can return a crafted version string containing JavaScript payload. Adminer inserts this string into script tags that have valid Content Security Policy nonces, effectively bypassing CSP protections and executing arbitrary code in the victim's browser. Any user who accesses Adminer while connected to the malicious server is vulnerable.

**Affected Features / Interoperability:** Adminer's database connection interface and its handling of server metadata. The vulnerability does not affect the MySQL server itself but rather the Adminer client tool. Downstream impact is limited to Adminer users; no direct MySQL server compromise occurs.

**Source:** https://github.com/vrana/adminer/security/advisories/GHSA-h6jr-7pr6-grgj, https://www.vulncheck.com/advisories/adminer-before-cross-site-scripting-via-mysql-version-string

**Actions:**
- Fix: Upgrade Adminer to version 5.4.3 or later.
- Workaround: Avoid using Adminer to connect to any MySQL servers outside of fully trusted, administrator-controlled environments. Treat all database server metadata as untrusted input.
- Tradeoff: Restricting Adminer connections limits administrative flexibility for development and troubleshooting against untrusted or third-party database endpoints.

#### MySQL — CVE-2026-71073 (CVSS 5.5 MEDIUM)
**Summary:** Oracle MySQL Connectors/ODBC version 26.7.0 contains a vulnerability that allows a local attacker with logon access to the system where the connector runs to cause a denial of service (complete hang or crash). Exploitation requires human interaction and local access; it cannot be exploited remotely without first compromising the endpoint.

**Affected Features / Interoperability:** The MySQL Connector/ODBC component specifically. Downstream impact includes any application relying on ODBC connectivity to MySQL databases; service disruption would affect database-dependent applications using this connectivity method.

**Source:** https://www.oracle.com/security-alerts/cspuaug2026.html

**Actions:**
- Fix: Apply the patched version per Oracle's Critical Patch Update for August 2026 when available.
- Workaround: Restrict local access to systems running MySQL Connector/ODBC; enforce least-privilege access controls on connector endpoints.
- Tradeoff: No significant functional tradeoff from access restrictions, but may impact legitimate local administrative use cases.

#### PostgreSQL — CVE-2026-50736 (CVSS 7.5 HIGH)
**Summary:** The pglogical replication extension's queue mechanism, which handles out-of-band commands like replicated DDL from publisher to subscriber, executes message payloads at the subscriber's apply worker privilege level—equivalent to a PostgreSQL superuser by default. An attacker controlling a publisher can send crafted queue messages to cause arbitrary SQL execution on the subscriber as superuser, achieving full database compromise from a role permitted to use pglogical. In typical deployments, exploiting this requires superuser-level subscription creation privileges, making this most relevant to managed environments where such privileges have been delegated to non-superuser roles.

**Affected Features / Interoperability:** pglogical replication extension, specifically the queue command delivery mechanism between publisher and subscriber nodes. This breaks tenant isolation in shared deployments and can compromise the entire subscriber database. Integrations relying on pglogical for logical replication are at risk.

**Source:** https://www.enterprisedb.com/docs/security/advisories/cve202650736/

**Actions:**
- Fix: Patch to the version containing the fix (verify current latest patched release with vendor).
- Workaround: Do not delegate subscription creation privileges to non-superuser roles; restrict pglogical to superuser-only administration. Audit existing pglogical subscriptions and their creation permissions.
- Tradeoff: Restricting subscription creation limits multi-tenant automation and self-service replication setup; may require manual DBA intervention for subscription changes.

#### PostgreSQL — CVE-2026-50737 (CVSS 7.5 HIGH)
**Summary:** pglogical's apply worker executes default column expressions on the subscriber at superuser privilege level by default. An attacker controlling a publisher can send replicated rows that trigger these default expressions, causing arbitrary functions to execute as superuser on the subscriber. This is an independent privilege escalation path separate from CVE-2026-50736, targeting the default expression evaluation mechanism rather than the queue command mechanism. Same conditions and audience apply.

**Affected Features / Interoperability:** pglogical replication, specifically row apply processing and default expression evaluation on subscriber nodes. Affects tables with DEFAULT expressions involving functions. Downstream risk is identical to CVE-2026-50736: full superuser compromise of the subscriber.

**Source:** https://www.enterprisedb.com/docs/security/advisories/cve202650737/

**Actions:**
- Fix: Patch to the version containing the fix (verify current latest patched release with vendor).
- Workaround: Same as CVE-2026-50736—do not delegate subscription creation privileges to non-superuser roles. Additionally, audit tables with DEFAULT expressions that invoke functions.
- Tradeoff: Same as CVE-2026-50736.

#### PostgreSQL — CVE-2026-76848 (CVSS 7.5 HIGH)
**Summary:** TypeORM's SelectQueryBuilder.distinctOn accepts raw user input without validation or escaping. For PostgreSQL-family drivers, this unsanitized input is interpolated directly into a `SELECT DISTINCT ON` SQL expression without going through identifier escaping or the driver's escape helpers. An attacker who can control the distinctOn parameter (for example, through an API that allows callers to specify deduplication columns) can inject arbitrary SQL expressions including correlated subqueries. This allows reading data anywhere the application's database role has access, bypassing the intended entity-level access controls.

**Affected Features / Interoperability:** TypeORM's SelectQueryBuilder component when used with PostgreSQL, specifically the distinctOn functionality. Applications that expose distinctOn to untrusted callers are vulnerable. Downstream impact includes unauthorized data disclosure across any tables the application's database role can access, regardless of the queried entity's intended permissions.

**Source:** https://github.com/typeorm/typeorm, https://www.vulncheck.com/advisories/typeorm-through-sql-injection-via-selectquerybuilder-distincton

**Actions:**
- Fix: Update TypeORM to the patched version (verify current latest release addressing this).
- Workaround: Never expose distinctOn parameter to untrusted callers; implement strict allowlist validation for any distinctOn values passed from user input. If distinctOn flexibility is required, route through validated, hardcoded identifiers only.
- Tradeoff: Restricting distinctOn limits API flexibility for dynamic query deduplication; may require application code refactoring to use alternative approaches.

#### PostgreSQL — CVE-2026-32286 (CVSS 7.5 HIGH)
**Summary:** The Go pg library's DataRow.Decode function does not properly validate field lengths. A malicious or compromised PostgreSQL server can send a DataRow message containing a negative field length value, causing a slice bounds out of range panic on the client side. This crashes the client application, resulting in a denial of service for any application using the pg library to connect to the malicious server.

**Affected Features / Interoperability:** The pg (jackc/pgx) Go library's protocol parsing, specifically DataRow message handling. Applications written in Go using this library to connect to PostgreSQL are affected. Downstream impact includes client-side crashes causing application unavailability.

**Source:** https://github.com/advisories/GHSA-jqcq-xjh3-6g23, https://pkg.go.dev/vuln/GO-2026-4518

**Actions:**
- Fix: Update the pg library to the patched version (verify current latest Go module version addressing this).
- Workaround: Ensure database server connections are only to trusted, administrator-controlled PostgreSQL servers; do not allow applications to connect to untrusted or potentially compromised database endpoints.
- Tradeoff: No significant tradeoff from server trust assumptions in controlled environments.

#### PostgreSQL — CVE-2026-50738 (CVSS 5.3 MEDIUM)
**Summary:** A use-after-free condition exists in pglogical's worker signaling code. During normal replication operations, a worker structure can be dereferenced after its underlying slot has been freed or recycled. This is reachable by low-privileged users who can influence worker timing through permitted pglogical operations. In the typical case, this crashes replication workers, causing availability impact. In the worst case, a use-after-free in a PostgreSQL backend can potentially be leveraged for remote code execution at the backend's privilege level.

**Affected Features / Interoperability:** pglogical replication worker lifecycle management. Both availability (crash) and potential remote code execution scenarios are possible. In default installations, this runs at superuser-equivalent privilege, making it a high-impact issue despite the medium CVSS.

**Source:** https://www.enterprisedb.com/docs/security/advisories/cve202650738/

**Actions:**
- Fix: Patch to the version containing the fix (verify current latest patched release with vendor).
- Workaround: Same as CVE-2026-50736—restrict subscription creation to superusers. Monitor for unexpected pglogical worker restarts.
- Tradeoff: Same as CVE-2026-50736.

#### PostgreSQL — CVE-2026-76212 (CVSS 5.3 MEDIUM)
**Summary:** phpMyFAQ before version 4.1.7, when configured to use PostgreSQL via the native pgsql PHP extension, incorrectly declares an ESCAPE character ('=') in its LIKE query handling while the escape function actually prefixes wildcards with '|'. This makes wildcard escaping ineffective, leaving user-supplied `%` and `_` characters active. An unauthenticated attacker can submit these wildcards in the public FAQ search form to force broad pattern matches and expensive sequential scans, causing denial of service. The PDO PostgreSQL backend is unaffected, and this does not enable SQL injection or data exfiltration—it's strictly a DoS vector via wildcard injection.

**Affected Features / Interoperability:** phpMyFAQ's search functionality when using the native pgsql PHP extension for PostgreSQL. Does not affect phpMyFAQ with PDO PostgreSQL backend. Downstream impact is limited to search availability; no data access or modification is possible through this path.

**Source:** https://github.com/thorsten/phpMyFAQ/security/advisories/GHSA-5hx6-c293-588h

**Actions:**
- Fix: Upgrade phpMyFAQ to version 4.1.7 or later.
- Workaround: Switch phpMyFAQ to use the PDO PostgreSQL backend instead of the native pgsql extension.
- Tradeoff: Switching backends requires configuration change and testing; may impact performance characteristics if PDO backend behaves differently.

## Cloud Security

The most urgent item in this cloud security digest is CVE-2026-17107, a HIGH-severity vulnerability in Kubernetes multi-cluster management that enables an authenticated hub principal to escalate to cluster-admin on every managed cluster. While no CISA KEV-confirmed active exploitation is present in the current data, this flaw represents a critical trust boundary break in Red Hat Advanced Cluster Management for Kubernetes (RHACM) and multicluster-engine (MCE) environments. Other notable issues include a Docker Engine daemon code execution flaw (CVE-2026-41567) and an Apache CloudStack cross-tenant access control weakness (CVE-2026-62440), but the Kubernetes privilege escalation poses the most immediate risk to cloud infrastructure with multi-cluster orchestration.

### Formal Vulnerabilities

#### Kubernetes — CVE-2026-17107 (CVSS 8.5 HIGH)
**Summary:** A flaw in the cluster-proxy service-proxy component of Red Hat Advanced Cluster Management for Kubernetes (RHACM) and multicluster-engine (MCE) allows an authenticated hub principal to inject an `Impersonate-Group` header and escalate to cluster-admin on every managed cluster. The vulnerability arises because the service-proxy appends impersonation group headers without first removing caller-supplied values, and the spoke ServiceAccount holds unrestricted impersonation permissions.

**Affected Features / Interoperability:** The cluster-proxy service-proxy component is directly impacted. This weakness undermines the trust model between hub and spoke clusters, potentially breaking multi-cluster policy enforcement, resource synchronization, and centralized management functions. Any integration relying on the spoke ServiceAccount's impersonation capabilities could be subverted.

**Source:**
- https://access.redhat.com/errata/RHSA-2026:46885
- https://access.redhat.com/errata/RHSA-2026:47388
- https://access.redhat.com/errata/RHSA-2026:47735
- https://access.redhat.com/errata/RHSA-2026:47949
- https://access.redhat.com/errata/RHSA-2026:47953

**Actions:**
- **Fix:** Apply the patched releases provided in the referenced Red Hat Security Advisories (RHSA-2026:46885 through RHSA-2026:47953).
- **Workaround:** No specific workaround is documented in the available data; restrict the privileges of the spoke ServiceAccount and monitor impersonation header traffic as a defense-in-depth measure.
- **Tradeoff:** Not specified in the data.

#### Kubernetes — CVE-2026-4740 (CVSS 8.2 HIGH)
**Summary:** Improper validation of Kubernetes client certificate renewal in Open Cluster Management (OCM) enables a managed cluster administrator to forge a client certificate that can be approved by the OCM controller. This allows cross-cluster privilege escalation and may give an attacker control over other managed clusters, including the hub cluster.

**Affected Features / Interoperability:** The OCM controller's certificate approval process is impacted. This flaw could break the certificate-based trust between managed clusters and the hub, compromising multi-cluster isolation and enabling lateral movement across clusters.

**Source:**

#### Kubernetes — CVE-2026-50149 (CVSS 6.5 MEDIUM)
**Summary:** In Contour ingress controller versions 1.23.0 through 1.33.4, an `HTTPProxy` resource configured with both `.spec.virtualhost.tls.enableFallbackCertificate: true` and `.spec.virtualhost.jwtProviders` is not rejected. This allows clients that send no TLS SNI or an unrecognized SNI to bypass JWT verification and be proxied to upstream services without a valid token. The issue is fixed in Contour v1.33.5.

**Affected Features / Interoperability:** Contour's TLS fallback certificate and JWT provider features are impacted. Downstream, this can allow unauthenticated requests to reach services behind the ingress, breaking JWT-based access control for affected virtual hosts.

**Source:**
- https://github.com/projectcontour/contour/security/advisories/GHSA-g3xr-5w5j-w4q4

**Actions:**
- **Fix:** Upgrade to Contour v1.33.5 or later, which rejects invalid configurations and marks affected resources with a `TLSIncompatibleFeatures` status condition.
- **Workaround:** Do not enable `.spec.virtualhost.tls.enableFallbackCertificate` on `HTTPProxy` resources that also define `.spec.virtualhost.jwtProviders`. Remove one of the two settings to avoid the invalid configuration.
- **Tradeoff:** Disabling either the fallback certificate or JWT provider may break existing configurations that rely on both features for seamless TLS handling or token validation.

#### Kubernetes — CVE-2026-62440 (CVSS UNSCORED)
**Summary:** An improper access control vulnerability in Apache CloudStack's Kubernetes Service (CKS) plugin allows cross-tenant manipulation of a Kubernetes cluster while adding and removing nodes. This affects CloudStack versions 4.21.0.0 through 4.22.1.0. Users are recommended to upgrade to version 4.22.1.1 or later.

**Affected Features / Interoperability:** The CloudStack CKS plugin's node management functionality is impacted. This could break multi-tenant isolation, allowing one tenant to interfere with another cluster's node lifecycle and potentially compromise cluster integrity.

**Source:**

#### Docker — CVE-2026-41567 (CVSS 7.2 HIGH)
**Summary:** A vulnerability in Docker Engine (Moby) allows arbitrary code execution with full daemon privileges when a user uploads a compressed archive (xz or gzip) into a container that contains a trojanized decompression binary. The daemon incorrectly resolves decompression binaries from the container's filesystem instead of the host. This is fixed in Docker Engine 29.5.1 and moby/moby v2.0.0-beta.14.

**Affected Features / Interoperability:** The container archive upload functionality (`PUT /containers/{id}/archive` and `docker cp`) is impacted. This could allow container escape and host compromise, breaking isolation between containers and the host operating system.

**Source:**
- https://github.com/moby/moby/security/advisories/GHSA-x86f-5xw2-fm2r
- https://access.redhat.com/errata/RHSA-2026:37387
- https://access.redhat.com/errata/RHSA-2026:41030
- https://access.redhat.com/errata/RHSA-2026:42852
- https://access.redhat.com/errata/RHSA-2026:44622

**Actions:**
- **Fix:** Upgrade to Docker Engine 29.5.1 or moby/moby v2.0.0-beta.14.
- **Workaround:** Only run containers from trusted images; use authorization plugins to restrict access to the `PUT /containers/{id}/archive` endpoint; avoid piping compressed archives into containers created from untrusted images.
- **Tradeoff:** Authorization plugins may add operational complexity and could restrict legitimate archive upload workflows if not carefully configured.

#### Docker — CVE-2026-33997 (CVSS 6.8 MEDIUM)
**Summary:** A vulnerability in Docker Engine's plugin installation process allows the daemon to incorrectly accept a privilege set that differs from the one approved by the user, bypassing privilege validation. Plugins that request exactly one privilege are also affected because no comparison is performed. This is patched in version 29.3.1.

**Affected Features / Interoperability:** Docker plugin installation and privilege validation mechanisms are impacted. This could allow a plugin to gain more privileges than intended, potentially leading to host compromise or unauthorized access to Docker resources.

**Summary:** Renovate versions prior to 42.96.3 (and prior to 43.4.4 for the 43.x branch) fail to restrict environment variables to an allowlist when spawning child processes. This allows child processes (e.g., `npm install`, post-upgrade tasks) to inherit all environment variables of the Renovate process, potentially exposing secrets to insider or outside attackers.

**Affected Features / Interoperability:** Renovate's child process spawning and environment variable handling are impacted. Downstream, this could lead to credential leakage and unauthorized access to integrated services that rely on secrets stored in the Renovate process environment.
