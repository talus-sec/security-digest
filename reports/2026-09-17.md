# Security Digest — 2026-09-17

## Database

The most urgent item is the critical SQL injection flaw in MariaDB/MySQL (CVE-2026-44172, CVSS 9.1), which allows unauthenticated attackers to bypass escaping controls and execute arbitrary SQL when using the big5 character set, posing an immediate risk to data confidentiality and integrity.

### Formal Vulnerabilities

#### MySQL — CVE-2026-44172 (CVSS 9.1 CRITICAL)
**Summary:** MariaDB/MySQL versions 3.3.18 and 3.4.8 fail to properly escape user input when the big5 character set is used with `mysql_real_escape_string()`, enabling SQL injection via the text protocol. An attacker who can send crafted queries to the database server can exploit this without authentication.  
**Affected Features / Interoperability:** The MySQL/MariaDB server’s text protocol handling and escaping logic are impacted; successful exploitation could lead to arbitrary SQL execution, compromising data confidentiality, integrity, and availability, and affecting any application or service that relies on the database.  
**Source:**  
- https://github.com/MariaDB/server/security/advisories/GHSA-pv9p-5w55-55jm  
- https://jira.mariadb.org/browse/CONC-819  
- https://access.redhat.com/errata/RHSA-2026:30135  
- https://access.redhat.com/errata/RHSA-2026:43505  
- https://access.redhat.com/errata/RHSA-2026:47772  
**Actions:**  
- Fix: Upgrade to MariaDB/MySQL 3.3.19 or 3.4.9 (or later).  
- Workaround: Restrict network access to the database server to trusted hosts and disable the big5 character set if not required.  
- Tradeoff: Limiting character set support may break applications that depend on big5 encoding; network restrictions could affect legitimate remote clients.

## Cloud Security

The most urgent item this cycle is **CVE-2026-85596** (Traefik Kubernetes Ingress NGINX provider, CVSS 9.8 CRITICAL), an authentication bypass that causes Traefik to fall back to the entry point's default TLS configuration — which does not request a client certificate — when two Ingress objects share the same host, CA secret, and client-authentication mode. This directly undermines mTLS client-certificate enforcement on Kubernetes ingress routes, making routes configured with `nginx.ingress.kubernetes.io/auth-tls-verify-client: "on"` reachable without a client certificate. In a healthcare environment running mTLS-based service mesh or ingress, this is the highest-priority remediation target.

### Formal Vulnerabilities

#### Microsoft Azure — CVE-2026-75156 (CVSS 9.1 CRITICAL)
**Summary:** Apache Airflow FAB provider versions 3.7.3 through 3.8.0 do not validate the issuer or audience of Azure AD `id_token`s during OAuth login. Because signing keys are fetched from Microsoft's multi-tenant JWKS endpoint, an `id_token` minted in *any* Azure tenant — including one an attacker creates — passes signature verification, and username and role assignments are then read from that attacker-controlled token. Anyone able to register an Azure tenant can authenticate to the Airflow UI with no prior access to the deployment. The fix for CVE-2026-59243 was incomplete; operators who already applied that fix are still affected and must upgrade again.

**Affected Features / Interoperability:** The Apache Airflow FAB auth manager when configured with Azure AD as an OAuth provider. Downstream impacts include unauthorized access to the Airflow UI, potential privilege escalation via role assignments read from the attacker-controlled token, and compromise of any workflow or DAG accessible through the authenticated session. Database replication, client drivers, and extensions are not directly mentioned in the advisory.

**Source:**
- https://github.com/apache/airflow/pull/71735
- https://lists.apache.org/thread/n3l6z4jfdxj4p0t8l7m6olkq6xsc6f76
- https://www.cve.org/CVERecord?id=CVE-2026-59243

**Actions:**
- **Fix:** Upgrade to `apache-airflow-providers-fab` 3.8.1 or later.
- **Workaround:** No interim workaround is specified in the available data.
- **Tradeoff:** No significant tradeoff once the patched version is deployed.

#### Kubernetes — CVE-2026-85596 (CVSS 9.8 CRITICAL) 🔴 ACTIVELY EXPLOITED (CISA KEV)
**Summary:** Traefik versions >= v3.7.0 and <= v3.7.10 contain an authentication bypass in the Kubernetes Ingress NGINX provider. The TLS option generated for an Ingress carrying the `nginx.ingress.kubernetes.io/auth-tls-secret` annotation was named after the Ingress namespace and name. Two Ingress objects sharing the same host, the same client CA secret, and the same client-authentication mode produced two distinct TLS option names for that host. Traefik treats this as a TLS options conflict and falls back to the entry point's default TLS configuration, which does not request a client certificate, so a route configured with `nginx.ingress.kubernetes.io/auth-tls-verify-client: "on"` becomes reachable without a client certificate. Only the v3.7 line is affected; fixed in v3.7.11.

**Affected Features / Interoperability:** Traefik v3.7.x Kubernetes Ingress NGINX provider TLS option generation and client certificate authentication. Downstream impacts include complete bypass of mTLS client-certificate verification on affected routes, allowing unauthenticated access to services that require client certificates. This is particularly critical for healthcare environments relying on mTLS for service-to-service or external-to-internal authentication. Database drivers and extensions are not directly mentioned.

**Source:**
- https://github.com/traefik/traefik/security/advisories/GHSA-j994-9gqj-9hwq
- https://www.vulncheck.com/advisories/traefik-3.7-authentication-bypass-via-tls-option-conflict

**Actions:**
- **Fix:** Upgrade to Traefik v3.7.11 or later.
- **Workaround:** No interim workaround is specified in the available data. As a temporary measure, ensuring that no two Ingress objects share the same host with client-authentication mode could reduce exposure, but this is not confirmed as effective.
- **Tradeoff:** No significant tradeoff once the patched version is deployed.
