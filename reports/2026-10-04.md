# Security Digest — 2026-10-04

## Database

The single most urgent item within the Database scope this cycle is **CVE-2026-104055** affecting the Canonical Charmed PostgreSQL Snap (`postgresql-operator`). While no CISA KEV-confirmed active exploitation entries currently exist for database systems in this digest, the cleartext logging of the monitoring user's password by the `postgres_exporter` represents a critical credential exposure vector. For environments running Postgres in Kubernetes or cloud environments utilizing the charmed operator, any actor with read access to the application logs can trivially recover database credentials, bypassing standard secret management (such as Vault PKI/mTLS setups) and gaining read-only database access. Immediate action should be taken to upgrade to the patched stable revisions, especially on any multi-node clusters where centralized logging aggregates these host logs.

### Formal Vulnerabilities

#### PostgreSQL — CVE-2026-104055 (CVSS UNSCORED) 
**Summary:** The `postgresql-operator` charm runs a Prometheus `postgres_exporter` to collect metrics using a dedicated "monitoring" PostgreSQL user. On database connection errors, the exporter writes the monitoring user's password in cleartext to its logs. Any actor able to read those logs can recover the password, which grants read-only `pg_monitor` access to PostgreSQL. This is a logic/credential exposure flaw rather than a remote network exploit, requiring local or aggregated log access to trigger.

**Affected Features / Interoperability:** The flaw specifically impacts the metrics exporter component (`postgres_exporter`) of the `charmed-postgresql-snap` package. It compromises the security of the `pg_monitor` role credentials. The raw data does not specify further downstream integrations beyond the read-only `pg_monitor` access, but any centralized logging stack (e.g., Loki, ELK, Fluentd) collecting these exporter logs will retain plaintext copies of the database password.

**Source:**
- https://github.com/canonical/charmed-postgresql-snap/pull/305
- https://github.com/canonical/charmed-postgresql-snap/pull/307
- https://github.com/canonical/postgresql-operator/pull/1863
- https://github.com/canonical/postgresql-operator/security/advisories/GHSA-rcx7-7rh5-r542

**Actions:**
- **Fix:** Upgrade to the patched revisions in the dev track (14/edge) revisions 1189 (arm64) and 1190 (amd64), or the stable track (14/stable) revisions 1216 (arm64) and 1190/1217 (amd64).
- **Workaround:** Restrict OS-level filesystem permissions on the host to ensure only the `postgres_exporter` process and root can read the exporter's log files, and temporarily disable the exporter if connection instability is suspected.
- **Tradeoff:** Restricting log file permissions may prevent non-root monitoring tools or standard support utilities from reading the logs, potentially hindering debugging capabilities.
