# Security Digest — 2026-09-04

## Database

The single most urgent item in today's database digest is **CVE-2026-9586** under the PostgreSQL bucket — it's the only CISA KEV-confirmed actively exploited entry, a SQL injection in Sangoma Switchvox that lets an unauthenticated remote attacker run arbitrary SQL against the backend PostgreSQL database (with a CISA due date of 2026-09-05). Beyond that, PostgreSQL carries the bulk of the high-severity formal CVEs this cycle, including a critical 10.0 (Versa Director), a 9.8 (R2R), and several other SQL injection issues in third-party products. MySQL's Connector/Net and Connector/J also surface multiple high-severity Oracle CPU entries, and a shared Grafana CVE (CVE-2026-19475) impacts PostgreSQL, MySQL, and SQL Server data sources.

### Formal Vulnerabilities

#### PostgreSQL — CVE-2026-9586 (CVSS UNSCORED — CISA-confirmed active exploitation) 🔴 ACTIVELY EXPLOITED (CISA KEV)
**Summary:** An unauthenticated remote attacker can send a single crafted request to Sangoma Switchvox and execute arbitrary SQL statements against the backend PostgreSQL database, with potential escalation to remote code execution. CISA added this to KEV on 2026-09-02 with a remediation due date of **2026-09-05** and requires mitigation per BOD 26-04 or discontinuing use of the product.

**Affected Features / Interoperability:** Switchvox's PostgreSQL backend is fully exposed to the SQLi; downstream PBX call data, configurations, and credentials stored in Postgres are reachable. The raw data does not specify which Switchvox versions or modules are affected beyond the vendor product as a whole.

**Source:** https://nvd.nist.gov/vuln/detail/CVE-2026-9586

**Actions:**
- Fix: No patched version supplied in the data — follow Sangoma's vendor instructions as referenced in CISA KEV.
- Workaround: Discontinue use of the product if mitigations are unavailable; otherwise, isolate Switchvox from any network reachable by untrusted actors, monitor Postgres logs for anomalous statements, and ensure Postgres is not directly reachable from outside the Switchvox host.
- Tradeoff: Discontinuing use of Switchvox disrupts telephony; network isolation may break legitimate admin workflows. Both are preferable to confirmed unauthenticated RCE-to-SQL exposure.

#### PostgreSQL — CVE-2024-42450 (CVSS 10.0 CRITICAL)
**Summary:** Versa Director ships with a default shared Postgres password and, by default, listens on all network interfaces. An unauthenticated attacker can connect and administer the Postgres database or read local filesystem contents for privilege escalation. Exploitation status is "proof of concept in lab" per Versa, but the impact ceiling (full DB admin + privesc) earns the 10.0.

**Affected Features / Interoperability:** Versa Director's Postgres holds operational/configuration data and is required for High Availability; compromise of the database breaks HA functionality and exposes all SD-WAN operational state.

**Source:** https://security-portal.versa-networks.com/emailbulletins/6735a300415abb89e9a8a9d3

**Actions:**
- Fix: Upgrade to Versa Director 22.1.4 or later (auto-restricts Postgres/HA ports to peer directors).
- Workaround: For older releases, perform manual HA-port hardening per https://docs.versa-networks.com/Solutions/System_Hardening/Perform_Manual_Hardening_for_Versa_Director#Secure_HA_Ports, change the default Postgres password, and bind Postgres to localhost/internal interfaces only. Follow Versa's published Firewall guidelines.
- Tradeoff: Manual hardening increases operational complexity and HA port restriction may break HA peering if not applied symmetrically across the director cluster.

#### PostgreSQL — CVE-2026-82526 (CVSS 9.8 CRITICAL)
**Summary:** R2R (through 3.6.6) has a stacked SQL injection in its vector index creation endpoint. The `index name` parameter is string-formatted directly into a `CREATE INDEX` statement without quoting or an allowlist, letting an unauthenticated attacker execute arbitrary DDL/DML — including semicolon-separated statements — under the PostgreSQL superuser.

**Affected Features / Interoperability:** Vector index creation endpoint; downstream Postgres superuser means full read/write across all databases R2R manages, including any embedded credential stores or application data.

**Source:** https://github.com/SciPhi-AI/R2R/issues/2309, https://www.vulncheck.com/advisories/r2r-sql-injection-via-vector-index-creation-endpoint

**Actions:**
- Fix: Upgrade R2R beyond 3.6.6 (the data doesn't list a specific fixed version; check the project's GitHub).
- Workaround: Restrict network access to the vector index creation endpoint, front it with authentication, and run the R2R Postgres role with least privilege rather than superuser.
- Tradeoff: Reducing the Postgres role from superuser may break R2R features that legitimately require DDL-level permissions.

#### PostgreSQL — CVE-2026-72775 (CVSS 8.8 HIGH)
**Summary:** n8n before 1.123.67 / 2.31.5 / 2.32.1 has a SQL injection in the PostgresTrigger node. User-supplied channel, function, and trigger names are interpolated into SQL statements without escaping, letting an authenticated n8n user run arbitrary SQL against the connected Postgres database with the configured credential's privileges.

**Affected Features / Interoperability:** PostgresTrigger node specifically; downstream Postgres databases used by n8n workflows are exposed, including any data the workflow credential can reach.

**Source:** https://github.com/n8n-io/n8n/security/advisories/GHSA-jqwr-vx3p-r266, https://www.vulncheck.com/advisories/n8n-before-sql-injection-via-postgrestrigger-node

**Actions:**
- Fix: Upgrade n8n to 1.123.67, 2.31.5, or 2.32.1 or later.
- Workaround: Restrict who can author PostgresTrigger nodes (RBAC), and use a dedicated least-privileged Postgres role for n8n's connection.
- Tradeoff: A least-privileged role will lose access to schemas/triggers outside its grant, which may break existing workflows.

#### PostgreSQL — CVE-2026-85388 (CVSS 8.1 HIGH)
**Summary:** Worklenz (through 3.0.0) fails to validate the `sort-field` query parameter in pagination helpers, allowing authenticated users to inject arbitrary Postgres expressions into `ORDER BY` clauses. Time- and blind-based extraction can leak data — including password hashes from other tenants — across tenant boundaries. Described as an incomplete fix for CVE-2026-25947.

**Affected Features / Interoperability:** Pagination/sorting helpers across Worklenz controllers; multi-tenant data isolation is broken at the database layer, including cross-tenant credential exposure.

**Source:** https://github.com/Worklenz/worklenz/security/advisories/GHSA-f2f8-2ppj-85pf, https://github.com/Worklenz/worklenz/blob/v3.0.0/worklenz-backend/src/controllers/job-titles-controller.ts

**Actions:**
- Fix: Upgrade Worklenz beyond 3.0.0 (the data doesn't list a specific fixed release; track the GHSA).
- Workaround: Restrict Worklenz to trusted authenticated users only and add a WAF/reverse-proxy rule to strip non-alphanumeric characters from `sort-field` parameters.
- Tradeoff: Strict input filtering on `sort-field` may break legitimate UI sorting on custom columns.

#### PostgreSQL — CVE-2026-19475 (CVSS 6.5 MEDIUM)
**Summary:** An authenticated Grafana user who can query a SQL data source can bypass the fix for CVE-2026-33375 by injecting the `timeGroup` macro via a WHERE clause; evaluating it causes uncontrolled memory consumption that terminates the Grafana server (DoS). Microsoft SQL Server, PostgreSQL, and MySQL data sources are all affected.

**Affected Features / Interoperability:** Grafana SQL data-source macro expansion; the crash takes down the Grafana server process, breaking all dashboards relying on that instance.

**Source:** https://grafana.com/security/security-advisories/cve-2026-19475

**Actions:**
- Fix: Apply the Grafana patch referenced in the security advisory (specific version not given in the data).
- Workaround: Restrict who can author or edit SQL data-source queries in Grafana; consider read-only roles for dashboards.
- Tradeoff: No significant tradeoff beyond limiting data-source edit privileges.

#### PostgreSQL — CVE-2026-85689 (CVSS 6.5 MEDIUM)
**Summary:** llmware 0.4.6 string-interpolates filter/lookup values into SQL WHERE clauses without parameterization in both SQLite and PostgreSQL backends. The validator only allow-lists keys, never sanitizes values. On Postgres this enables boolean- and UNION-based SQLi; on SQLite it enables cross-collection/cross-document disclosure.

**Affected Features / Interoperability:** llmware `Library.block_lookup`, `Query.text_query_with_custom_filter`, and `Query.text_query_by_author_or_speaker`; any Postgres database backing llmware is exposed.

**Source:** https://github.com/llmware-ai/llmware/issues/1304, https://www.vulncheck.com/advisories/llmware-0.4.6-sql-injection-via-unescaped-filter-values

**Actions:**
- Fix: Upgrade llmware beyond 0.4.6 (specific version not in the advisory).
- Workaround: Run llmware against a dedicated least-privileged Postgres role and isolate the public API from untrusted callers.
- Tradeoff: A restricted Postgres role may reject some legitimate collection operations that require broader DML.

#### MySQL — CVE-2026-60193 (CVSS 8.5 HIGH)
**Summary:** Oracle CPU July 2026 issue in MySQL Connector/Net (9.7.0–9.7.1). A low-privileged attacker with network access via multiple protocols can compromise Connector/Net, with scope change — meaning attacks may impact additional products beyond the connector itself. Successful exploitation leads to full takeover of Connector/Net. Exploitation is rated difficult.

**Affected Features / Interoperability:** Connector/Net specifically (ADO.NET driver); any .NET application talking to MySQL through 9.7.0–9.7.1 is affected, and "scope change" implies potential pivot to other Oracle products.

**Source:** https://www.oracle.com/security-alerts/cpujul2026.html

**Actions:**
- Fix: Apply the Oracle CPU July 2026 patch (specific fixed version not given in the data — track the Oracle alert).
- Workaround: Restrict network access to MySQL Connector/Net endpoints and enforce least-privileged MySQL accounts.
- Tradeoff: No significant tradeoff.

#### MongoDB — CVE-2026-72600 (CVSS 7.5 HIGH)
**Summary:** A broken access control in Idurar ERP/CRM 4.1.0 — the `/download` router is mounted without authentication middleware, letting unauthenticated attackers enumerate MongoDB ObjectIds and download invoice PDFs containing customer PII.

**Affected Features / Interoperability:** Idurar ERP/CRM's `/download` router and the underlying MongoDB invoice collection — exposes customer PII and invoice data.

**Source:** https://github.com/idurar/idurar-erp-crm

**Actions:**
- Fix: No patched version given — track the GitHub repo.
- Workaround: Place an auth layer in front of `/download`, restrict by IP/VPN, and add ObjectId unpredictability if feasible (e.g., opaque tokens).
- Tradeoff: Adding auth in front of `/download` will break any legitimate unauthenticated download links.

#### MongoDB — CVE-2026-84970 (CVSS 6.2 MEDIUM)
**Summary:** A numeric truncation weakness in the MongoDB C++ Driver's BSON JSON parser. Very large text inputs can cause out-of-buffer reads, silently truncated document acceptance, or process termination. No MongoDB server or credentials are required; impact is confined to the calling process.

**Affected Features / Interoperability:** MongoDB C++ Driver's BSON library JSON parsing — affects any application that hands user-controlled text to the public JSON parsing API (e.g., embedding ingestion pipelines).

**Source:** https://jira.mongodb.org/browse/CXX-3547

**Actions:**
- Fix: Upgrade MongoDB C++ Driver to a version that includes the fix (specific version not in the data — track CDRIVER/CXX Jira).
- Workaround: Validate and bound input sizes before passing JSON to the driver; reject documents over a sane size cap.
- Tradeoff: Strict size caps may reject legitimate large document ingest jobs.

#### MongoDB — CVE-2026-84964 (CVSS 5.9 MEDIUM)
**Summary:** Double free in the OpenSSL-based TLS certificate revocation checking path of the MongoDB C Driver. A trusted TLS endpoint with specially crafted cert data can crash the connecting client. No authentication required at the TLS layer; only requires the client already trusts the endpoint.

**Affected Features / Interoperability:** MongoDB C Driver's TLS revocation path — affects client applications linking libmongoc and using TLS certificate revocation checks.

**Source:** https://jira.mongodb.org/browse/CDRIVER-6409

**Actions:**
- Fix: Upgrade MongoDB C Driver to a patched version (track CDRIVER-6409).
- Workaround: Disable CRL/OCSP revocation checking in the client if feasible for the deployment, or pin to a known-good set of CAs.
- Tradeoff: Disabling revocation checking weakens TLS posture against compromised intermediate CAs.

#### MongoDB — CVE-2026-84963 (CVSS 5.3 MEDIUM)
**Summary:** Incorrect numeric conversion in the C Driver BSON JSON parser — an unusually large text value may be silently shortened or dropped, while parsing still reports success. Attacker-supplied input can cause the application to hold data that does not match what was submitted.

**Affected Features / Interoperability:** MongoDB C Driver BSON JSON parsing; primarily affects embedding-style apps where the driver accepts untrusted text.

**Source:** https://jira.mongodb.org/browse/CDRIVER-6407

**Actions:**
- Fix: Upgrade MongoDB C Driver (track CDRIVER-6407).
- Workaround: Validate input sizes and verify parsed documents against expected schemas.
- Tradeoff: Schema verification adds CPU overhead but is generally no significant tradeoff.

#### MongoDB — CVE-2026-84968 (CVSS 5.3 MEDIUM)
**Summary:** Out-of-bounds read in BSON decoding in the PHP driver. Untrusted specially formed input can cause a small amount of adjacent process memory to be copied into an error message returned to application code — limited memory disclosure.

**Affected Features / Interoperability:** MongoDB PHP driver's BSON decoder — affects PHP applications that hand untrusted input directly to BSON parsing.

**Source:** https://jira.mongodb.org/browse/PHPC-2744

**Actions:**
- Fix: Upgrade MongoDB PHP driver (track PHPC-2744).
- Workaround: Sanitize and bound inputs before BSON parsing; suppress detailed BSON error messages from user-facing paths.
- Tradeoff: Suppressing detailed errors reduces debuggability.

#### MongoDB — CVE-2026-84966 (CVSS 5.1 MEDIUM)
**Summary:** Incorrect numeric type conversion in the C++ Driver's BSON document builder. An extremely large, non-terminated field name can cause an out-of-buffer read and process termination. No auth required; the calling app must supply the oversized name in a specific form.

**Affected Features / Interoperability:** MongoDB C++ Driver BSON builder — affects applications that construct BSON from untrusted field names (rare, but possible in dynamic-schema systems).

**Source:** https://jira.mongodb.org/browse/CXX-3548

**Actions:**
- Fix: Upgrade MongoDB C++ Driver (track CXX-3548).
- Workaround: Enforce strict field-name length and character validation in any code path that builds BSON from untrusted input.
- Tradeoff: Strict validation may reject legitimate dynamic field names.

#### MongoDB — CVE-2026-65645 (CVSS 4.3 MEDIUM)
**Summary:** Rocket.Chat (versions before 8.8.0 / 8.7.1 / 8.6.2 / 8.5.3 / 8.4.6 / 8.3.8 / 8.2.8 / 8.1.8 / 7.10.15) has a MongoDB operator-injection in the Meteor DDP methods `getThreadsList` and `getThreadMessages`. The REST equivalent was patched in v5.0; the DDP method was never given the same fix.

**Affected Features / Interoperability:** Rocket.Chat DDP layer; underlying MongoDB message/thread collections — affects private thread confidentiality.

**Source:** https://github.com/RocketChat/Rocket.Chat/pull/41814, https://hackerone.com/reports/3852135

**Actions:**
- Fix: Upgrade Rocket.Chat to one of the listed fixed versions.
- Workaround: Restrict who can authenticate against the affected DDP endpoints; front DDP with a reverse proxy that performs schema validation.
- Tradeoff: Schema-validating proxy may reject legitimate Rocket.Chat mobile/desktop clients if their payloads evolve.

#### MongoDB — CVE-2026-84967 (CVSS 4.3 MEDIUM)
**Summary:** The MongoDB VS Code extension composes a command line for an integrated terminal from a connection string without escaping special characters. A social-engineering flow where a developer accepts a user-supplied connection target and opens the extension's shell feature lets an attacker place arbitrary text into the command line.

**Affected Features / Interoperability:** MongoDB VS Code extension's shell/terminal integration — primarily a developer-workstation risk, not a server one.

**Source:** https://jira.mongodb.org/browse/VSCODE-798

**Actions:**
- Fix: Upgrade MongoDB VS Code extension (track VSCODE-798).
- Workaround: Train developers to never accept connection strings from untrusted sources and to review the extension's confirmation dialog carefully.
- Tradeoff: The developer training tradeoff is minimal but non-technical.

#### MongoDB — CVE-2026-84969 (CVSS 3.7 LOW)
**Summary:** Memory-handling error in the C Driver's BSON-to-JSON conversion helpers. A document with a binary field encoded to a caller-configured length limit can write a few bytes past the end of a heap buffer — small heap corruption.

**Affected Features / Interoperability:** MongoDB C Driver's BSON-to-JSON conversion — primarily affects applications that pre-configure truncation limits.

**Source:** https://jira.mongodb.org/browse/CDRIVER-6410

**Actions:**
- Fix: Upgrade MongoDB C Driver (track CDRIVER-6410).
- Workaround: Avoid configuring caller-side truncation limits on BSON-to-JSON conversion when feasible.
- Tradeoff: Removing the length cap means larger outputs and higher memory use.

   - Description: Moby is an open source container framework. In versions prior to 29.5.1 and in moby/moby v2 prior to v2.0.0-beta.14, when a compressed archive is uploaded to a container via `PUT /containers/{id}/archive` or piped through `docker cp -`, the daemon resolves decompression binaries (such as `xz` or `unpigz`) from the container's filesystem rather than the host's due to incorrect ordering of operations. A malicious container image containing a trojanized decompression binary can achieve arbitrary code execution with full daemon privileges, including host root UID and unrestricted capabilities, when a user uploads a compressed (xz or gzip) archive into that container. This issue is fixed in Docker Engine 29.5.1 and moby/moby v2.0.0-beta.14. Workarounds include only running containers from trusted images, using authorization plugins to restrict access to the `PUT /containers/{id}/archive` endpoint, and avoiding piping compressed archives into containers created from untrusted images.
   - Summary: Moby Docker daemon archive upload mishandles decompression binaries, allowing malicious container images with trojanized binaries to achieve arbitrary code execution with full daemon privileges; fixed in Docker Engine 29.5.1.
   - Affected Features/Interoperability: Docker Engine, container archive upload via PUT /containers/{id}/archive or docker cp -; affects code execution if untrusted images used. Downstream: host compromise via daemon privileges.
   - Source: reference URLs.
   - Actions: Fix: upgrade Docker Engine to 29.5.1 or moby/moby v2.0.0-beta.14. Workaround: only use trusted images, restrict archive endpoint via authorization plugins, avoid piping compressed archives into containers from untrusted images. Tradeoff: may limit ability to use certain container operations with untrusted images.
